[바이브코딩 18편] 코드 678줄, 지침 2,601줄 — 본선 시작 저장소 vibe-starter의 4커밋

14팀이 이틀 동안 각자 저장소를 열 때, 팀이 갈라지지 않게 미리 심어 둔 것. Next.js 16.4.3과 Supabase, Prisma 7을 붙인 56개 파일보다 먼저 읽어야 할 것은 AGENTS.md 133줄과 .agent/ 8개 473줄이었다. 이 글은 그 저장소를 클론해 줄을 세고, DB 연결의 네 겹과 실패해도 비밀을 흘리지 않는 점검 스크립트를 열고, 저장소가 스스로 “아직 검증하지 않았다”고 적어 둔 세 곳을 확인한다.

작성자 김강훈 교수 (동의과학대학교 물리치료과 교수·학과장 / DIT AI 허브센터 팀장)

2편에서 다룬 해커톤은 18팀 72명이 지원해 14팀이 본선에 올랐고, 본선은 이틀이었으며 결과물 제출 마감이 2026년 10월 30일 13시 30분이었다. 그 이틀 동안 각 팀이 만든 것은 자기 저장소다. 이번 편의 대상은 그 저장소들의 출발점, 공개 템플릿 skyman200/vibe-starter입니다.

결론부터 적겠습니다. 이 저장소는 제가 만든 것 중 코드가 가장 적고 문서가 가장 많은 저장소입니다. 추적 파일 56개 3,661줄 가운데 마크다운이 23개 2,601줄, TypeScript가 678줄입니다. 비율로는 코드 1줄마다 지침 3.8줄입니다. 그리고 이 저장소에서 가장 정교한 파일은 화면이 아니라 108줄짜리 TLS 릴레이였고, 가장 정직한 파일은 “아직 검증하지 않았습니다”라고 적힌 배포 문서였습니다.

이 글에서 쓰는 “실측”의 뜻 — gh repo clone skyman200/vibe-starter로 받은 저장소에서 git log·git ls-files·git show --stat·wc -l로 센 값, 각 파일을 직접 읽고 문자열을 센 값, gh repo view로 확인한 공개 메타데이터입니다. 라이브 페이지가 없는 템플릿 저장소이고, 이 작업 환경에는 Node.js가 없어 npm install·npm run build·npm run db:validate는 실행하지 못했습니다. 그래서 이 글에는 “빌드가 통과한다” 같은 문장이 없습니다.

1이 저장소는 앱이 아니라 출발선이다

저장소 설명란은 이렇게 시작합니다 — “DIT 바이브코딩 해커톤 본선 시작 저장소(Next.js · Supabase) — [Use this template]로 팀 저장소를 만든다”. 화면이 아니라 행동이 설명의 중심입니다. 팀은 이 저장소를 포크하는 게 아니라 Use this template으로 복사합니다. GitHub에서 템플릿 복사본은 포크로 집계되지 않습니다. 그래서 이 저장소의 포크 0·스타 0은 “아무도 안 썼다”는 뜻이 아니라 쓰임을 셀 수 없다는 뜻입니다. 실제로 공개 저장소를 검색해도 이 템플릿에서 나온 팀 저장소를 특정할 수 없었습니다. 이 저장소의 성과는 별 수로 증명되지 않습니다.

그래서 이 글은 성과 대신 구조를 봅니다. 팀이 처음 5분에 무엇을 읽게 되는지, 에이전트가 무엇을 하려다 멈추게 되는지, 어떤 실패가 미리 막혀 있는지. 시작 저장소의 품질은 그 세 가지로 갈립니다.

5AGENTS.md 133줄 — 에이전트에게 주는 다섯 가지

이 파일은 지시문이지 설명문이 아닙니다. 첫 절부터 “이 절차는 AGENTS.md 자체와 .agent/ 아래의 모든 지침 문서를 수정·추가하는 경우에 적용한다”로 시작합니다. 지침을 고치는 지침이 맨 앞에 있습니다. 그리고 지침 변경은 제안까지만 하고, “사용자가 명확히 승인한 경우에만” 적용하라고 못 박습니다.

이어지는 절은 다섯 가지 일을 합니다.

  • 프로젝트 목적을 한 문장으로 고정한다. “비개발자도 이해하기 쉬운 최소 Next.js 보일러플레이트를 유지한다. 요청하지 않은 예제 기능, 패키지, 복잡한 폴더 구조를 추가하지 않는다. 응답은 한국어로 작성하고 변경 이유와 영향을 쉬운 말로 설명한다.”
  • 상황별로 어떤 지침을 읽을지 매핑한다. 기능 개발, 화면·스타일, 서버, 오류 추적, 보안, DB, 배포, 협업 여덟 갈래에 각각 문서를 지정하고, “여러 영역에 걸치면 해당 문서를 모두 읽는다”고 붙입니다.
  • 작업 순서를 다섯 단계로 정한다. 요구사항 분석·계획 → DB 분석 → 서버 처리 → 화면 구현 → 연결·권한·동작 검증. 데이터 저장이 필요한 기능의 기본값이고, “화면만 바꾸는 작업에 DB 변경이나 서버 계층을 만들지 않는다”는 예외를 함께 답니다.
  • 승인의 경계를 그린다. 읽기 전용 확인은 진행, 수정·생성은 승인 뒤. 그리고 명시적 요청 없이는 절대 하지 않는 목록 — 파일 삭제·이동, 패키지 설치, lock·환경 변수·인증·권한·결제 변경, 마이그레이션 생성·실행, 실제 DB 데이터 변경, 배포, Git commit·push·pull·merge·rebase·reset.
  • 보안과 검증을 마지막에 묶는다. “비밀키, DB URL, 토큰, 실제 사용자 데이터를 코드·문서·로그·답변에 노출하지 않는다”, “비밀값 확인이 필요하면 전체 파일 출력 대신 변수 존재 여부 등 최소 정보만 확인한다”. 그리고 npm run check는 “타입·린트·포맷 검사이며 테스트나 실제 DB 연결 검증은 아니다”라고 스스로 한계를 적습니다.

“승인”이라는 낱말이 218번 — 지침 문서 전체에서 이 단어가 나오는 횟수를 세어 봤습니다. AGENTS.md 32회, .agent/ 75회, docs/ 80회, plans/README.md 31회. 합계 218회입니다. 2,601줄짜리 문서에서 열두 줄에 한 번꼴로 “승인”이 나옵니다. 이 저장소가 자동화를 가르치는 방식은 금지 목록을 크게 쓰는 것입니다.

여기에 재미있는 문장이 하나 있습니다. “문서 선택은 Codex가 이 안내에 따라 수행한다. .agent/ 전체가 자동 로딩된다고 가정하지 않는다.” 에이전트에게 자기 자신의 컨텍스트를 과신하지 말라고 적어 둔 것입니다. 그리고 “상황별 문서를 읽었다는 이유로 변경이나 명령 실행이 승인된 것으로 간주하지 않는다”가 따라붙습니다. 읽는 것과 하는 것을 분리한 문장이고, 이 저장소 지침의 성격을 한 줄로 보여 줍니다.

7docs/ 12개 — 저장소가 스스로 적은 검증 장부

8DB 연결의 네 겹 — CA 파일 하나를 배포까지 데려가는 방법

이 저장소에서 기술적으로 가장 밀도가 높은 부분은 화면이 아니라 연결 코드 255줄입니다. Supabase PostgreSQL에 붙는 일을 네 겹으로 나눠 놨습니다.

첫째 겹 — 환경 변수 두 개와 “URL로 검증을 끄지 마세요”

.env.example 25줄은 앱용과 CLI용 주소를 분리합니다. 앱은 Transaction pooler(6543), Prisma CLI·마이그레이션은 Direct 또는 Session pooler(5432)입니다. 그리고 주석에 이렇게 적습니다 — “sslmode·sslaccept·sslcert·sslrootcert 등 TLS 옵션은 URL에 직접 추가하지 마세요. 이 프로젝트의 연결 코드가 TLS 옵션을 정리하고 검증을 유지하도록 강제합니다.”

둘째 겹 — URL에서 TLS 옵션을 지우는 46줄

src/lib/database-tls.ts는 연결 문자열을 받아 ssl로 시작하는 모든 쿼리 파라미터와 uselibpqcompat을 지웁니다.

// URL options must never replace the CA or disable hostname verification.
for (const key of [...url.searchParams.keys()]) {
  const normalized = key.toLowerCase();
  if (normalized.startsWith('ssl') || normalized === 'uselibpqcompat') {
    url.searchParams.delete(key);
  }
}

그리고 풀 설정을 이렇게 고정합니다 — ssl: { ca: readSupabaseCa(), rejectUnauthorized: true, minVersion: 'TLSv1.2' }, max: 2, connectionTimeoutMillis: 5_000, idleTimeoutMillis: 10_000. 서버리스 환경에서 인스턴스마다 연결 두 개, 5초 안에 안 되면 실패, 10초 놀면 반납. 숫자가 아니라 상한을 정해 둔 것입니다. 누군가 ?sslmode=disable을 붙여도 코드가 지우기 때문에 검증이 꺼지지 않습니다.

셋째 겹 — pooler 주소를 거부하는 37줄

src/lib/prisma-tls.ts는 마이그레이션용 주소가 Transaction pooler(6543)이면 실행 전에 오류를 냅니다 — “DIRECT_URL에는 Transaction pooler가 아닌 Direct 또는 Session pooler 주소를 입력해 주세요.” 마이그레이션이 풀러를 통과하면 원인을 찾기 어려운 실패가 되기 때문에, 실패를 친절한 문장으로 앞당긴 것입니다. 그리고 Prisma 엔진은 node-postgres의 SSL 설정을 쓰지 않으므로, sslmode=require·sslaccept=strict·sslcert 경로를 URL에 직접 넣습니다.

넷째 겹 — macOS에서만 도는 108줄짜리 릴레이

src/lib/prisma-tls-relay.ts는 이 저장소에서 가장 예상 밖의 파일입니다. 주석이 이유를 그대로 말합니다 — “Prisma’s migration engine checks TLS with the macOS certificate policy, which rejects the Supabase pooler certificate (no extended key usage, five-year validity) even with the correct CA.” 즉 CA가 맞아도 macOS 정책이 거부합니다. 선택지는 둘입니다. 검증을 끄거나, 검증을 유지한 채 우회하거나. 이 저장소는 후자를 골랐습니다.

// PostgreSQL SSLRequest message: length 8, request code 80877103.
const SSL_REQUEST = Buffer.from([0, 0, 0, 8, 4, 210, 22, 47]);

동작은 이렇습니다. mkdtempSync('/tmp/prisma-tls-')로 권한 0700 폴더를 만들고(다른 사용자는 접속 불가), 그 안의 유닉스 소켓을 엽니다. Prisma CLI는 이 소켓에 평문 PostgreSQL로 붙습니다. 릴레이는 원격에 8바이트 SSLRequest를 보내고, 돌아온 응답이 정확히 한 글자 S(0x53)일 때만 TLS를 시작합니다. TLS는 Node가 certs/supabase-ca.crt로 호스트명까지 검증하고(rejectUnauthorized: true, TLS 1.2 이상, IP면 SNI 생략), 성공한 뒤에야 양쪽을 파이프로 잇습니다. 프로세스가 끝나면 임시 폴더를 지웁니다.

비판도 함께 적겠습니다. 이 108줄은 macOS 분기에서만 동작합니다(process.platform === 'darwin'). Windows·Linux에서는 CLI가 인증서 경로를 담은 URL로 직접 붙습니다. 즉 이 코드는 한 운영체제의 정책 차이를 메우는 우회로이고, 우회로는 언제든 낡습니다. Prisma나 macOS 정책이 바뀌면 이 파일은 조용히 필요 없어지거나 조용히 깨집니다. 그런데도 이 선택이 옳았던 이유는 분명합니다. 비개발자에게 “TLS 검증을 끄세요”라고 가르치지 않으려고 108줄을 쓴 것입니다. 시작 저장소가 가르치는 첫 습관이 “검증 끄기”가 되면, 그 팀은 3일 뒤 운영에서 같은 습관을 반복합니다.

다섯째 겹 — 인증서를 배포 번들에 넣는 20줄

next.config.ts에는 눈에 잘 안 띄지만 결정적인 두 줄이 있습니다.

outputFileTracingIncludes: {
  '/*': ['./certs/supabase-ca.crt'],
},

이게 없으면 서버리스 함수 번들에 CA 파일이 빠져 배포 환경에서만 certs/supabase-ca.crt를 읽을 수 없습니다가 납니다. 로컬에서는 잘 되고 배포에서만 깨지는, 가장 찾기 싫은 종류의 실패입니다. 여기에 poweredByHeader: false(서버 헤더로 프레임워크를 알리지 않음)와 cacheComponents·partialPrefetching이 함께 있습니다.

9check-db.ts 159줄 — 실패해도 비밀을 흘리지 않는 점검

npm run db:check가 부르는 scripts/check-db.ts는 이 저장소의 사상이 가장 압축된 파일입니다. 하는 일은 “연결되는지 보는 것”인데, 그 안에 안전 규칙이 네 개 들어 있습니다.

  • 인증서를 먼저 검사한다. new X509Certificate(readSupabaseCa())로 CA 여부와 유효기간을 확인하고, 아니면 DB에 붙기 전에 멈춥니다. “공개 CA 형식·위치·유효기간을 확인하세요.”
  • 두 주소를 다른 방식으로 본다. DATABASE_URL은 앱과 같은 드라이버로 SELECT 1, DIRECT_URL은 prisma db pull --print — 스키마 파일도 DB도 쓰지 않는 읽기 전용 조회입니다. CLI는 셸이 아니라 require.resolve로 설치된 경로를 찾아 실행합니다(다운로드·OS별 바이너리 가정 없음).
  • 빈 DB를 정상으로 읽는다. P4001(조회할 테이블 없음)은 실패가 아니라 “Prisma CLI 접속 성공 (조회할 테이블 없음)”으로 처리합니다. 첫 마이그레이션 전 상태를 오류로 만들지 않습니다.
  • 오류를 다섯 문장으로만 바꾼다. 드라이버 오류에는 호스트·사용자·스키마 조각이 섞여 나옵니다. 이 스크립트는 원문을 출력하지 않고 다섯 갈래로 분류해 고정 문구만 냅니다 — 비밀번호·URL 인코딩, CA·TLS, 네트워크·방화벽, 시간 초과, 기타. 그리고 마지막 줄에 “테이블·데이터·마이그레이션·스키마 파일은 변경하지 않았습니다”를 찍습니다.

이 파일이 하는 일은 사실 별것 아닙니다. 연결 확인입니다. 그러나 실패했을 때 무엇을 말하지 않을지를 코드로 정해 둔 점이 다릅니다. 비개발자가 오류 화면을 캡처해 채팅에 붙이는 것이 일상인 팀에서, 붙여도 되는 오류를 만드는 것은 기능입니다.

11plans/ 215줄 — 계획 양식이 정한 세 가지

plans/README.md는 215줄이고, 그중 115줄이 복사해 쓰는 계획 양식입니다. 양식은 열 개 절 — 목표, 포함·제외 범위, 화면·사용 흐름, 현재 구조, 수정 대상 표, 작업 순서, 완료 기준, 승인 범위와 근거, 진행 상태와 검증 결과, 변경 이력. 여기서 세 가지가 눈에 띕니다.

첫째, 파일명이 시각과 작성자를 요구합니다. YYYYMMDD-HHmmss-작성자-작업명.md, 시각은 KST, 콜론은 금지(Windows 호환). 같은 초에 겹치면 짧은 식별자를 덧붙이고, 기존 파일을 덮어쓰지 않습니다.

둘째, 작성자를 추측하지 말라고 못 박습니다. “package.json의 author는 보일러플레이트 원 제작자 정보일 수 있으므로 자동 사용하지 않습니다”, “Git의 user.name은 GitHub 사용자명과 다를 수 있으므로 확인 없이 대체하지 않습니다”. 실제로 이 저장소의 author는 progdper입니다. 템플릿을 복사한 팀의 계획 파일에 원 제작자 이름이 박히는 사고를 문서가 미리 막습니다. 그리고 “에이전트가 파일을 대신 작성했다는 이유로 작성자에 codex를 넣지 않습니다”가 붙습니다.

셋째, 승인과 검증을 네 층으로 분리합니다. 사용자 승인 / 구현 결과 / 검증 결과 / 실제 DB·배포 적용. “파일을 만들었다는 이유만으로 기능을 완료로 표시하지 않습니다. 검사 명령·성공 또는 실패·미검증 범위를 함께 남깁니다.” 계획의 체크 표시가 새 권한이 되지 않는다는 문장도 있습니다.

12본선 이틀과 이 저장소 — 마지막 커밋이 찍힌 시각

2편에 적은 일정을 다시 가져오면, 행사는 2026년 9월 28일부터 10월 30일까지였고 본선은 14팀·2일, 결과물 제출 마감이 10월 30일 13시 30분, 코드 심사는 14팀×3회로 42회였습니다. 이 저장소의 마지막 커밋은 10월 28일 11시 27분, 마감 이를 앞둔 오전입니다. 그 커밋이 고친 6줄은 앞서 본 대로 TLS 릴레이의 실패 경로와 검증 강제였습니다.

여기서 조심할 것이 있습니다. 본선 팀들이 실제로 이 템플릿을 복사했는지는 확인할 수 없습니다. 템플릿 복사본은 포크로 집계되지 않고, 공개 저장소를 검색해도 이 템플릿에서 나온 팀 저장소를 특정할 수 없었습니다. 저장소의 포크 0·스타 0은 그 사실의 증거가 아닙니다. 다만 저장소 설명과 마지막 커밋의 시각이 가리키는 것은 분명합니다 — 이 저장소는 행사 중에 쓰이도록, 행사 중에 마지막 손질이 들어간 물건입니다.

그리고 이 대목이 18편을 쓰는 이유이기도 합니다. 2편은 심사하는 쪽(플랫폼)의 기록이었고, 이번 편은 심사받는 쪽이 처음 열게 되는 것의 기록입니다. 해커톤의 품질은 심사위원이 몇 명인지보다, 참가자가 첫 5분에 무엇을 읽는지에서 갈립니다.

13없는 것 목록 — 이 저장소가 일부러 비워 둔 자리

  • 테스트 0개. 스크립트 15개에 test가 없습니다. npm run check는 타입·린트·포맷이고, 문서 스스로 “테스트나 실제 DB 연결 검증은 아니다”라고 밝힙니다. 이틀짜리 팀에게 테스트를 강요하지 않은 선택으로 읽히지만, 결과물 심사에서 테스트가 배점에 들어간다면 시작점이 그 항목을 가르쳐 주지 않는 셈입니다.
  • 마이그레이션 0개. prisma/schema.prisma는 18줄에 User 모델 하나(UUID id, 고유 email, 선택 name, 생성·수정 시각, @@map("users"))이고 prisma/migrations 폴더가 없습니다. 팀이 처음 db:migrate:dev를 실행할 때가 첫 마이그레이션입니다.
  • CI 0개. .github/가 없습니다. docs/GITHUB_ACTIONS.md 103줄이 “필요할 때 도입하는 선택”으로 예시를 제공하고, AGENTS.md는 “요청 없이 생성하지 않는다”고 막습니다.
  • 인증 0개. User 모델은 있는데 비밀번호·세션 모델이 없고, Supabase Auth와의 연결도 없습니다. 문서는 이 사실을 숨기지 않고 선택지 비교(170줄)만 제공합니다.
  • 배포 검증 0개. 라이브 주소가 없고, 문서가 “아직 검증하지 않았습니다”라고 적습니다.
  • README는 빈 양식입니다. 45줄에 “(앱 이름)”, 그리고 프로젝트 개요·주요 기능 표·기술 스택·실행 방법·AI 활용 내역·팀원 역할·아쉬운 점. 빈칸이 16개입니다. 특히 “AI 활용 내역”의 하위 항목이 인상적입니다 — “주요 프롬프트(그대로 붙여 넣기)”, “AI가 만든 것 / 사람이 고친 것”, “결과를 확인한 방법”. README의 절반은 코드 설명이 아니라 심사자가 읽을 칸입니다.

이 목록은 흠이 아니라 설계의 흔적입니다. 스타터 킷이 모든 것을 넣으면 팀은 아무것도 결정하지 않습니다. 대신 비워 두면 팀이 결정합니다. 문제는 비워 둔 자리가 README에 적혀 있지 않다는 점입니다. 어디까지가 주어졌고 어디부터가 팀의 몫인지는 문서를 다 읽어야 알 수 있습니다.

14이 저장소가 남긴 세 문장

비밀키, DB URL, 토큰, 실제 사용자 데이터를 코드·문서·로그·답변에 노출하지 않는다.— AGENTS.md 「보안과 인코딩」
파일을 만들었다는 이유만으로 기능을 완료로 표시하지 않습니다. 검사 명령·성공 또는 실패·미검증 범위를 함께 남깁니다.— plans/README.md 「승인과 완료 기록」
이 보일러플레이트는 실제 Vercel 배포와 배포 주소에서의 DB 읽기·쓰기를 아직 검증하지 않았습니다.— docs/VERCEL_DEPLOYMENT.md 「현재 배포 검증 상태」

세 문장이 같은 것을 말합니다. 모르는 것을 아는 것처럼 쓰지 않는다. 첫 문장은 사람에게, 둘째는 팀에게, 셋째는 자기 자신에게 하는 말입니다. 2,601줄짜리 문서에서 실제로 오래 남는 것은 기능 설명이 아니라 이 세 줄이라고 생각합니다.

15한계 — 지침이 코드보다 많으면 생기는 일

  • 지침도 썩습니다. 코드 1줄에 지침 3.8줄인 저장소는 코드를 고칠 때마다 문서를 함께 고쳐야 합니다. 그 규율이 깨지면 지침은 틀린 안내가 되고, 틀린 안내를 따르는 에이전트는 사람이 세운 규칙보다 위험합니다. AGENTS.md가 “실제 폴더 구조나 실행 명령이 문서와 달라진 경우” 지침 개선을 제안하라고 적어 둔 이유가 이것입니다.
  • 이력이 이유를 말하지 않습니다. 커밋 네 개의 메시지가 모두 시각입니다. 12,787줄이 한 커밋으로 들어온 순간, 팀은 무엇이 왜 바뀌었는지 git log로 알 수 없습니다. 이 저장소의 유일한 기록 수단은 문서입니다.
  • 릴레이는 우회로입니다. macOS 분기 108줄은 운영체제 정책이 바뀌면 함께 바뀌어야 합니다. 이 글에서 이 코드가 실제로 동작하는지 확인하지 못했습니다(이 환경에 Node가 없습니다).
  • 검증의 범위가 좁습니다. 저장소 자신이 밝힌 대로 Windows 로컬 연결만 확인됐고, Linux·Vercel·마이그레이션·읽기/쓰기는 미검증입니다. “검증 완료”라는 문구를 봤을 때 어디까지인지 반드시 옆줄을 읽어야 합니다.
  • 오류 추적 지침이 16줄입니다. 팀이 실제로 막히는 순간에 꺼내 볼 문서가 가장 얇습니다.
  • 쓰임을 셀 수 없습니다. 템플릿 복사본은 포크로 집계되지 않습니다. 이 저장소가 몇 팀의 첫 커밋이 되었는지는 GitHub 지표로 알 수 없습니다.

16Q&A

Q1.이 저장소로 앱이 바로 돌아가나요?

첫 화면은 DB 없이 뜹니다. 스크립트 15개 중 dev·build·start가 있고 postinstall이 prisma generate를 돌립니다. 다만 DB 기능은 .env의 DATABASE_URL이 있어야 하고, 인증·CRUD 화면·테스트는 없습니다. 저장소도 “실제 Vercel 배포와 배포 주소에서의 DB 읽기·쓰기를 아직 검증하지 않았습니다”라고 적습니다.

Q2.왜 코드보다 문서가 3.8배인가요?

사용자가 두 명이기 때문입니다. 한 명은 팀, 다른 한 명은 그 팀의 AI 에이전트입니다. 사람에게는 docs/ 12개 1,735줄, 에이전트에게는 AGENTS.md 133줄과 .agent/ 8개 473줄을 줍니다. 그 문서 전체에 “승인”이라는 낱말이 218번 나옵니다.

Q3.108줄짜리 TLS 릴레이는 무엇을 하나요?

macOS에서만 동작합니다. Prisma 마이그레이션 엔진이 macOS 인증서 정책으로 Supabase pooler 인증서를 거부하기 때문에, CLI는 권한 0700 임시 폴더의 유닉스 소켓에 붙고 릴레이가 대신 SSLRequest(80877103)를 보내 S 한 글자를 확인한 뒤 Node의 검증 TLS로 이어 붙입니다. 검증을 끄는 대신 108줄을 쓴 선택입니다.

Q4.우리 팀 시작점으로 써도 되나요?

라이선스는 MIT이고 저작권 고지는 원 제작자 progdper에게 있습니다. package.json의 author도 원 제작자이므로, docs/CUSTOMIZE_PROJECT.md의 절차대로 프로젝트 정보를 바꾸되 LICENSE의 MIT 고지는 보존해야 합니다. AGENTS.md도 “작성자 정보는 승인 후 변경할 수 있지만 LICENSE와 원 제작자의 MIT 고지는 보존한다”고 적습니다.

Q5.커밋이 4개뿐인데 개발 기록은 어디에 있나요?

없습니다. 네 메시지가 모두 “시작 저장소 + 시각”이라 이유가 이력에 남지 않았습니다. 대신 결정의 이유는 docs/와 .agent/의 문장으로 남겼습니다. 이 저장소에서 이력은 개발 과정이 아니라 스냅숏 네 장이고, 기록의 역할은 문서가 대신합니다.

17에필로그 — 시작점의 품질은 첫 5분에 정해진다

이 저장소를 다시 열면서 가장 오래 본 것은 page.tsx도, AGENTS.md도 아니었습니다. 10월 28일 11시 27분의 6줄이었습니다. 마감 이를 앞두고 누군가 고친 것이 새 기능이 아니라 “응답이 오기 전에 끊기는 경우”와 “검증을 끄지 못하게”였다는 사실이, 이 저장소가 무엇을 중요하게 여겼는지 가장 정확하게 말해 줍니다.

1년 동안 시스템 22개를 만들면서 매번 느낀 것이 있습니다. 프로젝트는 대개 실력이 아니라 시작점에서 갈립니다. 첫 5분에 무엇을 읽고, 첫 실패에서 무엇을 배우고, 첫 화면에서 어떤 말투를 익히는지. 이 저장소는 그 5분을 위해 코드 678줄 옆에 지침 2,601줄을 두었습니다. 과한 것 같지만, 팀에게 남는 것이 화면이 아니라 습관이라면 과하지 않습니다.

좋은 시작 저장소는 답을 주지 않는다. 무엇을 물어야 하는지를 남긴다.

저장소는 github.com/skyman200/vibe-starter에 공개 템플릿으로 있습니다. 이 글의 커밋·파일·줄 수는 git log·git show --stat·wc -l로, 문자열 횟수는 파일에서 직접 세었고, 공개 메타데이터는 gh repo view로 확인했습니다. 이 환경에 Node.js가 없어 설치·빌드·DB 점검은 실행하지 못했으며, 저장소 자신도 Vercel 배포 검증을 하지 않았다고 적고 있습니다. 확인하지 못한 것은 확인하지 못했다고 적었습니다.
