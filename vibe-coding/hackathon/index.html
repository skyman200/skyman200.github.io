1. 프롤로그: 행사는 공지문이 아니라 소프트웨어다

2026년 가을, 동의과학대학교에서 '2026 DIT 바이브코딩 해커톤'을 열었습니다. 정원 100명·25팀 규모로 접수를 열었고, 18팀 72명이 지원했습니다. 의무 교육과 48시간 예선을 거쳐 14팀이 본선에 올랐고, 이틀 동안 각 팀이 새 저장소에서 서비스를 만들어 배포한 뒤, 마지막 날 오후에 결과물을 두 갈래로 심사했습니다.

  • 대면 심사 50점 — 문제 정의·기획 15, 완성도·사용성 15, 창의성 10, 발표·질의응답 10
  • 코드 심사 50점 — 기술 구현 15, AI 활용 15, 코드 품질 10, 문서화 10

코드 심사는 14팀을 팀마다 3회씩, 총 42회 채점한 평균입니다. 그 42회를 사람이 붙잡고 있었던 것은 아닙니다. 운영 담당 컴퓨터 한 대에서 AI가 42번 채점하고, 점수만 서버로 올라갔습니다.

이 글은 그 시스템을 어떻게 만들었는지에 대한 기록입니다. 결론부터 말하면, 이 프로젝트의 본질은 '해커톤 앱'이 아니라 행사 운영체제(Event OS) 였습니다. 신청, 팀빌딩, 공문서 생성, 예선 과제 배정, 제출물 검증, 익명 심사, 시상까지 — 행사의 모든 상태 변화가 하나의 URL 안에서 일어나야 했기 때문입니다.

"학생은 링크 하나만 받는다. 운영진은 엑셀을 열지 않는다. 심사위원은 점수만 넣는다. 나머지는 시스템이 한다."

이 문장이 지난 두 달 동안 얼마나 많은 설계 결정을 바꿨는지, 아래에 하나씩 풀어 보겠습니다.

참가자가 실제로 걷는 길

  1. 안내 — 주소를 열면 바로 행사 안내와 남은 접수 기간이 보인다.
  2. 팀 만들기 — 팀장이 팀명·대표 학과·참가 주제·프로젝트명·활용 AI 도구·참가 동기를 넣는다.
  3. 4인 팀빌딩 — 초대 링크를 받은 팀원 3명이 각자 본인 정보를 넣고 본인이 동의한다. 4명이 모이기 전에는 제출 버튼이 열리지 않는다(서버도 4명이 아닌 제출을 거절한다).
  4. 신청서 제출 — 누르는 순간 공지 별첨 양식 그대로의 한글(.hwpx)·PDF가 자동 생성되어 운영진 드라이브로 간다. 올릴 파일은 없다.
  5. 의무 교육 → 예선 시작 — 교육 끝에 강사가 띄운 6자리 세션 코드를 넣으면 24개 과제 중 아직 뽑히지 않은 하나가 무작위로 배정되고 48시간이 시작된다.
  6. 예선 제출 — 앱 주소 또는 공개 GitHub 저장소 + 앱 소개 + 만든 과정. 서버가 앱 주소를 직접 열어 "남이 로그인 없이 볼 수 있는 주소인지" 확인한다.
  7. 본선 — 새 저장소를 등록하고 이틀 동안 개발한다. 저장소는 5분마다 자동 점검된다(공개 여부, README 필수 6항목, .env 유출). 마감 뒤에는 팀원 전원이 만족도 조사에 답해야 최종 제출이 된다.
  8. 심사·시상 — 코드 심사 50 + 대면 심사 50. 시상 결과를 켜면 참가현황 맨 위에 수상 팀이 뜬다.

이 여정 전체가 단 하나의 URL에서 일어납니다. 학생 입장에서 앱 설치도, 회원가입도, 별도 링크도 없습니다.

화면 11개는 '역할'로 나뉜다

역할화면인증
참가자안내 · 참가 신청 · 초대 합류 · 참가현황 · 내 신청이메일·비밀번호
운영관리자(칸반·설정·서류) · 예선 · 본선 · 심사발급 코드
현장심사위원 · 강사 교육 콘솔 · 교육 따라 하기 · 멘토 · 행사장 TV코드 또는 무인증

여기서 초보자가 가장 많이 하는 실수는 한 화면에 모든 역할을 넣는 것입니다. 행사는 단계마다 사용자가 바뀝니다. 신청 기간의 주인공은 학생, 교육 시간의 주인공은 강사, 본선의 주인공은 멘토와 심사위원입니다. 역할이 바뀌면 화면도 바뀌어야 하고, 화면이 바뀌면 상태 기계(state machine) 도 바뀝니다.

그래서 이 시스템의 진짜 설계도는 UI가 아니라 상태 전이표입니다. 팀 구성 중 → 접수 완료 → 본선 진출/예비/미선발 → 개발 중 → 결과물 제출 → 심사 완료 — 이 여섯 상태를 벗어나는 데이터는 하나도 없게 만들었습니다.

3. 아키텍처 분석: 제약이 설계를 정했다

3.1 예산 0원, 계정 1개, 동시 접속 100명

이 프로젝트에는 세 가지 제약이 있었고, 그 제약이 사실상 아키텍처를 결정했습니다.

  1. 예산이 없다. 서버를 빌릴 수 없다. 학교가 이미 쓰는 구글 워크스페이스 계정 안에서 끝내야 한다.
  2. 운영자가 개발자가 아니다. 행사 당일 운영은 조교와 행정직원이 한다. 터미널, 배포 명령, 로그 확인을 요구할 수 없다.
  3. 접수 마감 직전에 트래픽이 몰린다. 100명이 거의 같은 시간에 접속한다. 학과 단톡방에 링크가 뿌려지는 순간이다.

이 세 문장이 "AWS에 스프링 부트"를 "GitHub Pages + Vercel + Apps Script"로 바꿨습니다. 화려한 선택이 아니라 제약에 맞는 유일한 선택이었습니다.

3.2 네 개의 계층

Architecture 
[브라우저]
 ├─ 화면(정적 파일) ─────────────▶ GitHub Pages
 ├─ 공개 읽기(설정·참가현황) ─────▶ Vercel 함수 + CDN 캐시(서울) ──▶ Apps Script
 ├─ 오류 보고 ──────────────────▶ Vercel 함수 → 디스코드(개인정보 삭제 후)
 └─ 신청·로그인·관리·심사 ───────▶ Apps Script 웹앱
                                    ├─ 원본 데이터: PropertiesService(스크립트 속성)
                                    ├─ 사본·감사 기록: Google Sheets
                                    ├─ 신청서(HWPX/PDF)·제출본(zip): Google Drive
                                    └─ 트리거: 5분마다 점검·동기화·저장소 감시

[운영 담당 컴퓨터]
 ├─ 가린 심사 묶음 받기 ◀──────── Apps Script
 └─ AI 채점 도우미(127.0.0.1:8790) → 그 컴퓨터의 AI → 점수만 업로드

각 계층의 역할이 읽기/쓰기/무거운 연산으로 갈라져 있다는 점이 핵심입니다.

  • GitHub Pages는 그냥 파일 서버다. 빌드 도구 없이 Preact + htm으로 만든 단일 페이지 앱을 올린다.
  • Vercel 함수는 읽기 전용 캐시 계층이다. 설정과 참가현황을 CDN에 캐시하고, 동시에 몰린 요청을 하나로 합친다(coalescing).
  • Apps Script는 유일한 쓰기 경로다. 인증, 상태 변경, 파일 생성이 모두 여기를 지난다.
  • 운영 PC의 로컬 도우미는 CPU를 오래 쓰는 작업(브라우저 자동화, AI 호출)을 맡는다. Apps Script의 6분 실행 제한과 무관해진다.

이 분리는 성능 최적화가 아니라 실패 격리입니다. 읽기 계층이 죽어도 신청은 되고, 쓰기 계층이 느려도 첫 화면은 뜹니다.

3.3 77개 action과 '내 요청의 답' 검증

Apps Script 웹앱은 REST 리소스가 아니라 단일 엔드포인트 + action 이름 구조입니다. POST 본문에 {action: 'teamCreate', ...}가 들어가고, 서버는 모든 응답에 같은 action을 실어 돌려줍니다. 77개 기능이 이 규약 하나를 공유합니다.

이 작은 규약이 실제로 사고를 막았습니다.

실제 사고

운영 중, 어떤 POST가 중간 프록시에서 본문 없는 GET으로 바뀌어 서버에 도착한 적이 있습니다. 서버는 doGet으로 답했고, 그 응답이 CDN에 캐시되면서 뒤에 온 사람들까지 깨진 화면을 봤습니다.

해결은 단순했습니다. 응답이 내가 보낸 요청의 답인지 확인하는 것.

// 서버는 모든 답에 action 을 싣는다.
export function answers(data, action) {
  return !!data && typeof data.ok === 'boolean' && data.action === action;
}

action이 다르거나 없으면 "답을 받지 못한 것"으로 취급합니다. 화면은 그때부터 추측하지 않고 상태를 다시 읽습니다.

3.4 재시도는 '두 번 해도 되는가'로 설계한다

네트워크가 흔들릴 때 무작정 재시도하면 최악의 버그가 생깁니다. 팀이 두 번 만들어지고, 코드가 두 번 발급되고, 알림이 두 번 갑니다. 그래서 재시도 규칙을 코드가 아니라 의미로 나눴습니다.

구분의미처리
BUSY서버가 요청을 받고 아무것도 바꾸지 않았다(잠금 획득 실패)항상 재시도
NETWORK답을 못 받았다(반영됐을 수도 있음)멱등한 요청만 재시도
 
export const NO_NETWORK_RETRY = new Set([
  'adminCode', 'adminJudgeAdd', 'adminJudgeReset', 'adminJudgeRemove',
  'adminMemberRemove', 'adminDeleteTeam', 'adminPurge', 'adminPinReset',
  'meWithdraw', 'meUpdate', 'teamDissolve', 'teamKick', 'teamTransfer',
  'teamInvite', 'adminPrelimSession', 'adminTeachCode', 'prelimSubmit',
  'teachStart', 'adminMentorCode', 'mentorHelp',
]);

export const MAX_ATTEMPTS = 6;
export const FIRST_WAIT_MS = 700;
export const MAX_WAIT_MS = 8000;

재시도는 최대 6회, 700ms에서 시작해 두 배씩 늘어 최대 8초, 여기에 0.5~1.5배 지터를 섞습니다(같은 순간에 몰린 클라이언트가 동시에 다시 때리지 않도록).

가장 어려운 판단은 prelimSubmit이었습니다. 예선 제출은 서버가 제출된 앱 주소를 직접 열어 보고 GitHub 저장소 압축본(최대 30MB)을 받아 보관합니다. 끊겼을 때 다시 보내면 서버가 같은 일을 겹쳐 합니다. 그래서 다시 보내지 않고, 호출한 쪽이 제출 상태를 다시 읽습니다. 반대로 심사 묶음 받기나 점수 올리기는 같은 요청을 다시 보내도 같은 결과라서 재시도를 허용했습니다.

교훈. 재시도는 네트워크 기능이 아니라 도메인 지식이다. "이 요청이 두 번 실행되면 무슨 일이 생기는가"를 답할 수 있어야 재시도를 켤 수 있다.

3.5 배포는 '불변 폴더'로

정적 사이트의 고전적 문제는 캐시된 옛 화면 + 새 API 조합입니다. 그래서 배포마다 스크립트를 내용 해시 폴더에 넣습니다.

/v/81d46dad295f/assets/app.js
/v/a9bfe9cd95de/assets/app.js
/version.json  →  {"id":"a9bfe9cd95de","at":"2026-11-01T13:23:00.454Z"}

이미 열려 있는 화면은 1분 이하 간격으로 version.json을 확인하고, 새 버전이 있으면 스스로 새로고침합니다. 단, 입력 중이거나 한 번만 보이는 코드(세션 코드·심사 코드)가 떠 있으면 안내만 하고 기다립니다. 행사 중에 화면이 갑자기 새로고침되면 학생이 작성하던 신청서가 날아가기 때문입니다.

3.6 개인정보 경계를 코드로 긋는다

이 시스템에서 개인정보는 세 곳에서 통제됩니다.

  1. 서버가 원문을 보내지 않는다. 공개 참가현황은 이름을 김*훈으로, 학번·연락처·이메일은 흐리게 처리한 값만 내려보냅니다. 개발자 도구를 열어도 원문이 없다.
  2. 오류 보고에서 개인정보를 지운다. 화면에서 한 번, 디스코드로 보내기 전에 한 번 더.
  3. 심사 AI에게 개인정보가 가지 않는다. 아래 병목 3에서 자세히 다룹니다.
// 이메일·전화번호·6자리 이상 숫자(학번 등)를 지운다. 스크립트 주소는 남긴다.
.replace(/[\w.+-]+@[\w-]+(?:\.[\w-]+)+/g, '<email>')
.replace(/\d{2,3}[-. ]\d{3,4}[-. ]\d{4}/g, '<phone>')
.replace(/\d{6,}/g, '<num>')

4. 병목 1: 구글 시트를 DB로 쓴 대가 — 3초 락

4.1 증상

첫 버전은 구글 스프레드시트를 원본 데이터베이스로 썼습니다. 접수 첫날, 팀원 75명이 같은 시간에 합류 버튼을 눌렀습니다. 결과는 몇 분씩 밀리는 지연이었습니다. 어떤 학생은 "저장 중" 화면에서 3분을 기다렸습니다.

4.2 원인

SpreadsheetApp은 행을 쓸 때마다 문서 단위 잠금을 잡습니다. 실측으로 쓰기 1회당 약 3초. 게다가 우리 로직은 전형적인 read-modify-write였습니다.

1. 전체 팀 목록을 읽는다
2. 메모리에서 팀 상태를 바꾼다
3. 전체 목록을 다시 쓴다   ← 여기서 3초 잠금

동시 요청이 10개만 겹쳐도 대기열이 만들어지고, 대기열이 길어지면 타임아웃이 나고, 타임아웃이 나면 클라이언트가 재시도해서 대기열이 더 길어지는 악순환이었습니다.

4.3 실패한 시도

  • 시트 분산: 팀별 시트로 나눠 봤지만 잠금은 문서 단위라 효과가 없었습니다.
  • 배치 append: 행 추가를 모아서 해도 읽기-수정-쓰기 구간은 줄지 않았습니다.
  • CacheService: 빠르지만 휘발성이고 원자성이 없습니다. 정원 초과를 막을 수 없습니다.

4.4 해결: 락을 피하지 말고, 락 구간을 0.1초로 줄여라

구조를 바꿨습니다.

  • 원본은 PropertiesService(스크립트 속성)에 JSON 한 덩어리로 둔다. 단일 문서이므로 트랜잭션 경계가 명확하다.
  • 모든 쓰기는 하나의 전역 LockService 잠금 안에서 read-modify-write를 끝낸다. 잠금 안에서는 I/O를 하지 않는다(드라이브 업로드, 외부 API 호출은 잠금 밖으로 뺀다).
  • 시트는 원본이 아니라 보기용 사본이다. 5분마다 자동 갱신되고, 사람이 고쳐도 원본에 반영되지 않는다.
  • 정원·중복 검사는 잠금 안에서 수행한다. "25팀"과 "학번 중복 금지"는 분산 환경의 낙관적 검사로는 절대 못 막는다.

결과는 3초 → 0.1초대. 같은 조건의 실측은 이렇습니다.

시나리오결과
100명 동시 열람3.1초 안에 모두 응답
팀장 25명 동시 팀 만들기가장 늦은 사람 6.8초
팀원 75명 동시 합류절반 9.0초, 가장 늦은 사람 19.7초
팀장 25명 동시 제출(신청서 생성 포함)가장 늦은 사람 16.1초
교훈. 병목은 "느린 함수"가 아니라 직렬화된 구간이다. 코드를 빠르게 만드는 것이 아니라, 남이 기다리는 구간을 짧게 만들어야 한다.

5. 병목 2: 공문 양식 — HWPX와 PDF가 1:1로 같아야 한다

5.1 요구사항이 이상하게 구체적이었다

공지는 이렇게 적혀 있었습니다.

"참가 신청서는 [별첨] 양식에 따라 작성하여 제출하여야 한다."

대학 행정에서 이 문장은 곧 "한글 파일과 PDF가 공지 양식과 똑같아야 한다"는 뜻입니다. 표의 칸 위치, 글꼴, 줄바꿈, 쪽 나눔까지. 스캔해서 공문철에 넣을 것이기 때문입니다.

5.2 왜 어려운가

문서의 모양은 데이터가 아니라 조판 엔진(typesetting engine) 이 결정합니다. 같은 텍스트라도 렌더러가 다르면 줄이 바뀌는 위치가 다릅니다.

  • HTML → PDF: 브라우저의 줄바꿈 규칙(CSS)은 한글 조판 규칙과 다릅니다. 특히 표 안에서 음절 단위 줄바꿈, 자간, 행 높이가 어긋납니다.
  • LibreOffice 변환: DOCX/HWPX를 PDF로 바꾸면 글꼴 대체가 일어나고 표 높이가 달라집니다.
  • 실제로 두 방법 모두 "비슷하지만 다른" 문서를 만들었고, 원본과 겹쳐 보면 즉시 티가 났습니다.

5.3 해결 A — HWPX는 '양식에 글만 채운다'

HWPX는 OWPML(XML) 기반 컨테이너입니다. 새로 그리지 않고, 공지 별첨 파일 자체를 템플릿으로 열어 표 셀과 누름틀에 값만 주입했습니다. 조판은 한컴오피스가 하므로, 원본과 같은 엔진에서 같은 결과가 나옵니다.

  • 표 셀: 팀명·대표 학과·참가 주제·프로젝트명·개요·팀원 4명 정보
  • 파일명: 학과_팀명_참가신청서.hwpx

5.4 해결 B — PDF는 한글의 규칙을 코드로 옮긴다

PDF는 다른 문제였습니다. HWPX를 PDF로 변환하려면 서버에 한컴오피스가 있어야 하는데, Apps Script에는 그런 것이 없습니다. 그래서 한글의 배치 규칙을 직접 구현했습니다.

  • 글꼴: 맑은 고딕, HY헤드라인M, 함초롬돋움. 필요한 글자만 서브셋으로 embed.
  • 줄바꿈: 한글 음절 단위 줄 나눔, 금칙 문자(숫자·단위·괄호) 처리.
  • 표: 행 높이·열 너비·셀 여백을 원본 좌표에서 그대로 가져와 그린다.
  • 쪽 나눔: 표가 쪽 경계를 넘을 때 머리행 반복과 분할 규칙.

5.5 검증은 '눈으로'가 아니라 '겹쳐서'

가장 중요한 단계는 검증이었습니다. AI는 "양식과 동일하게 만들었습니다"라고 말합니다. 그 말을 믿지 않고, 생성된 PDF를 한컴오피스 화면 위에 반투명으로 겹쳐 줄과 칸이 어긋난 곳을 찾았습니다. 어긋난 지점마다 좌표를 고치고 다시 겹쳤습니다. 이 반복이 전체 개발 기간에서 가장 지루하고 가장 중요한 시간이었습니다.

결과: 신청서 1건 생성 약 6~10초 (보충 글꼴이 필요한 이름이면 9~17초). 25팀이 동시에 제출해도 가장 늦은 사람이 16.1초.

교훈. "같아 보인다"와 "겹쳐도 같다"는 다르다. 품질 기준을 말로 두지 말고 파일로 두어라.

6. 병목 3: 42회 AI 코드 심사 — 익명성·재현성·운영성의 삼중 제약

6.1 세 가지 요구가 서로를 밀어낸다

  1. 익명성: 심사하는 AI가 학생의 이름·학번·저장소명을 알면 안 된다. (개인정보 국외 이전 동의 범위 밖이기도 하다.)
  2. 재현성: 생성형 AI의 채점은 한 번 돌릴 때마다 흔들린다. 그런데 시상은 공정해야 한다.
  3. 운영성: 행사 당일 운영자는 개발자가 아니다. 터미널을 열 수 없다.

이 셋을 동시에 만족시키는 구조는 "가림은 서버, 실행은 로컬, 판단은 AI" 로 역할을 쪼개는 것이었습니다.

6.2 파이프라인

Pipeline 
[Apps Script]
  1) 마감 시각의 최신 커밋을 확정 (커밋에 적힌 시각은 믿지 않는다)
  2) 코드에서 성명·학번·저장소명·비밀값(.env)을 제거
  3) 무작위 심사 번호 부여 (S-01 … S-14)
  4) 심사 묶음을 관리자 화면으로 내려줌
        │
        ▼
[운영 담당 컴퓨터 · 채점 도우미 127.0.0.1:8790]
  5) 팀별 격리 환경에서 코드를 읽고(본선) / 앱을 직접 써 보고(예선)
  6) 같은 팀을 3회 채점 → 항목별 평균
  7) 근거(회차별 점수·메모)는 이 컴퓨터에만 저장
        │
        ▼
[Apps Script]  ← 점수만 업로드
  8) 3회 평균을 표에 반영, '직접 입력으로 바꿈' 흔적과 경고 표시
  9) 순위·동점·시상 계산

서버는 AI를 부르지 않습니다. 이 원칙이 개인정보 문제와 실행 시간 문제를 동시에 해결했습니다. Apps Script에는 6분 실행 제한이 있고, 외부 AI 호출 비용도 서버에 붙이면 안 됩니다.

6.3 익명화는 '가리는 척'이 아니라 삭제

심사 묶음을 만들 때 서버는 다음을 문자열에서 제거합니다.

  • 학생 성명, 학번, 이메일, 연락처
  • GitHub 저장소 이름과 소유자 핸들(팀 식별이 가능하므로)
  • .env, API 키, 토큰 형태의 문자열
  • 커밋 메시지에 들어간 이름

그리고 S-01 같은 무작위 심사 번호만 붙입니다. 번호와 팀의 매핑은 서버에만 있고, 심사 AI와 채점 도우미는 매핑을 모릅니다. 점수가 올라온 뒤에 서버가 번호를 팀으로 되돌립니다.

6.4 격리는 '컨테이너 + 새 브라우저' 두 겹

학생 코드는 신뢰할 수 없습니다. 악성 코드일 수도 있고, 실수로 무한 루프일 수도 있습니다.

  • 컨테이너: 권한 없는 사용자, 읽기 전용 파일 시스템, 네트워크는 프록시를 통해서만. 사설망(127.0.0.1, 10.x, 192.168.x) 차단.
  • 브라우저: 팀·회차마다 새 프로필. 쿠키·로컬스토리지가 다음 팀으로 넘어가지 않는다.
  • 본선 코드 심사는 코드를 실행하지 않는다. 줄 번호를 붙여 읽기만 한다. (예선 채점은 반대로, 학생이 배포한 앱을 실제로 써 본다. 두 심사의 목적이 다르다.)

6.5 왜 3회 평균인가

생성형 AI에게 100점 만점 채점을 시키면, 같은 코드에도 회차마다 5~10점이 흔들립니다. 한 번의 점수로 시상하면 AI의 기분에 상을 주는 것과 같습니다.

그래서 세 가지를 겹쳤습니다.

  1. 3회 반복 + 항목별 평균 (표준편차가 큰 팀은 화면에 표시)
  2. 루브릭 고정: 항목과 배점을 프롬프트에 명시하고, 각 점수의 근거를 한 줄씩 요구
  3. 휴먼 오버라이드: 운영자가 필요하면 직접 입력으로 바꿀 수 있고, 바꾼 팀은 표에 '직접 입력을 바꿈'으로 남는다
항목배점채점 기준(요약)
기술 구현15기능이 실제로 동작하는가, 예외 처리는 있는가
AI 활용15AI를 도구로 썼는가, 결과를 검증했는가
코드 품질10구조·가독성·중복·보안
문서화10README 6항목, 실행 방법, AI 활용 내역
합계503회 평균

6.6 실패를 전제로 만든 안전장치

  • 도우미 버전 불일치: 화면과 도우미가 주고받는 방식에 판(version)을 두었다. 현재 4. 불일치하면 화면이 "도우미를 다시 실행하세요"라고 알린다.
  • 중복 업로드: 같은 점수 파일을 다시 올려도 같은 결과가 되도록 했다(멱등).
  • 일부 회차 실패: 3회 중 하나라도 실패하면 점수 올리기 버튼이 잠기고, 실패한 회차 목록을 보여 준다. "평균 2회"로 조용히 넘어가지 않는다.
  • 마감 이후 커밋: 마감 1초 뒤의 최신 커밋을 서버가 기록한다. 커밋에 적힌 시각은 작성자가 조작할 수 있어 신뢰하지 않는다.
교훈. AI 심사의 본질은 점수가 아니라 파이프라인이다. 누가 무엇을 보고, 무엇을 남기고, 무엇을 올리는지를 설계해야 한다.

7. 병목 4: 첫 화면 3초 — 100명이 동시에 들어와도

7.1 Apps Script의 숙명

Apps Script 웹앱은 첫 응답에 수 초가 걸립니다(콜드 스타트 + 인증 + 스크립트 파싱). 접수 마감 10분 전에 100명이 몰리면, 첫 화면이 뜨기도 전에 학생들이 링크를 다시 누릅니다. 트래픽이 두 배, 세 배가 됩니다.

7.2 세 겹의 방어

  1. 미리 그려 넣기(prerender): 배포할 때 크롬으로 첫 화면을 실제 렌더링해 HTML에 넣는다. 주소를 열면 서버 응답을 기다리지 않고 즉시 안내·일정·남은 기간이 보인다.
  2. 읽기 전용 CDN 계층: 설정·참가현황은 Vercel 함수(서울 리전)가 캐시한다. 100명이 같은 데이터를 요청해도 Apps Script에는 거의 요청이 가지 않는다.
  3. 요청 병합(coalescing): 같은 순간에 들어온 동일 요청은 하나로 합쳐 한 번만 Origin에 묻는다.

여기에 화면 쪽 최적화를 더했습니다. 참가현황은 30초 폴링(웹소켓 아님), 탭이 숨겨져 있으면(document.visibilityState === 'hidden') 폴링을 멈춘다. 행사장 TV처럼 계속 켜 두는 화면이 서버를 낭비하지 않게.

7.3 결과

구간이전이후
첫 화면 표시2~4초(서버 대기)즉시(정적 HTML)
참가현황 갱신매번 Origin30초 캐시 + 병합

교훈. 서버를 늘리는 대신 요청을 줄인다. 캐시는 기능이 아니라 예산이다.

8. 병목 5: 행사 당일의 실시간성

행사장에서 시스템은 '웹사이트'가 아니라 사회기반시설입니다. 전원이 꽂혀 있고, TV에 현황이 떠 있고, 멘토가 호출되고, 마감 시각에 커밋이 고정되어야 합니다.

8.1 5분마다 도는 것들

  • 신청서 파일 점검: 드라이브에서 지워졌거나 내용과 다르면 다시 만든다.
  • 보기용 시트 갱신: 운영진이 엑셀처럼 보는 사본.
  • 본선 저장소 재점검: 공개 여부, README 필수 6항목(개요·주요 기능·기술 스택·실행 방법·AI 활용 내역·팀원 역할), .env 유출.
  • 예선 마감 알림: 마감 직전 제출이 반영되도록 7분 유예.
  • 디스코드 알림 재전송: 알림이 실패하면 5분 안에 다시.

8.2 마감 1초 뒤의 커밋 고정

심사의 공정성은 "어느 시점의 코드를 심사했는가"에 달려 있습니다. 그래서 제출 마감 1초 뒤에 본선 팀 저장소의 최신 커밋 SHA를 서버가 기록합니다. 이후 커밋은 심사에 들어가지 않습니다. 커밋 메시지에 적힌 시각은 작성자가 바꿀 수 있으므로, 서버가 관찰한 시각만 믿습니다.

8.3 멘토 호출은 상태 기계다

요청 → (멘토)가는 중 → 완료 — 세 상태뿐이지만, 동시성 문제가 있습니다. 두 멘토가 같은 팀을 동시에 잡으면? 그래서 멘토의 처리 요청에는 기대 상태를 함께 보냅니다. 그사이 상태가 바뀌었으면 "그사이 바뀜"으로 거절하고 목록을 다시 읽습니다. 낙관적 잠금의 교과서적 형태입니다.

8.4 무대까지 코드로

시상식 화면은 LED 매트릭스 연출입니다. 팀 이름을 작은 격자에 4배로 그려 칸마다 덮인 양으로 점을 켜고, 트로피 등장과 조명 효과를 CSS가 아니라 캔버스로 그립니다. 행사장 TV 현황판은 지금/다음 일정과 팀 상태를 큰 글씨로 보여 줍니다. "동작 줄이기(prefers-reduced-motion)" 설정이면 모션을 멈춥니다.

교훈. 행사용 소프트웨어의 완성도는 기능 개수가 아니라 당일 아침에 운영자가 몇 번 클릭하는가로 측정된다. 목표는 0번이다.

- 의무 교육은 [90]분, 강사 혼자 진행한다. 강사가 버튼으로 진행하는 화면과 학생이 따라 하는 화면, 인쇄용 진행 지침서를 만들어라. 진행표·대본·요청 글의 원본은 한 곳에 두고 화면과 지침서가 같이 쓰게 해라.

9.1 해 보고 알게 된 것

  1. 백엔드·드라이브 계정은 처음에 정한다. 중간에 바꾸면 스크립트·드라이브·시트를 통째로 옮겨야 한다. 이번에 실제로 백엔드 계정을 중간에 옮겼다.
  2. 구글 시트를 원본(DB)으로 쓰면 동시 신청이 몇 분씩 밀린다. 스크립트 속성에 두고 시트는 보기용 사본으로만 쓴다.
  3. Apps Script는 첫 응답에 수 초 걸린다. 공개 화면은 Vercel 캐시로, 첫 화면은 미리 그려서 넣는다.
  4. HTML로 만든 PDF·LibreOffice 변환은 한글 양식과 달랐다. 한글 배치 규칙대로 직접 그리는 코드를 만들고 한글 화면과 겹쳐 확인했다.
  5. AI가 "완료"라고 해도 운영 주소에서 더미로 끝까지 해 봐야 진짜 문제가 보인다. 샘플 파일이 폴더에 안 남는 문제, PDF 양식 차이가 그렇게 발견됐다.
  6. 서버가 200을 줘도 그 답이 내가 보낸 요청의 답인지 확인해야 한다. POST가 중간에서 본문 없는 GET으로 바뀌어 오는 일이 실제로 있었고, 엉뚱한 답이 CDN에 캐시되자 뒤에 온 사람까지 깨진 화면을 봤다.
  7. 오류를 콘솔에만 찍고 버리면 다시 재현할 수 없다. 개인정보만 지워 운영 채널로 보고하게 해 두니 다음 제보에서 원인 줄을 바로 찾았다.
  8. 채점처럼 무거운 일은 서버가 아니라 운영 담당 컴퓨터에서 돌린다. 관리자 화면 버튼이 그 컴퓨터의 서비스를 부르게 하면 운영자는 터미널을 몰라도 된다.
  9. 단계가 늘어나는 행사는 '누가 어느 화면을 쓰는지'를 먼저 정해야 화면이 뒤섞이지 않는다.
  10. 관리자 코드·비밀번호 같은 비밀값은 저장소·노션·단톡방에 올리지 않는다.

10. 185개 테스트 — '데모'와 '운영'을 가르는 것

  • PropertiesService, SpreadsheetApp, DriveApp, LockService를 메모리 구현으로 바꿔 끼우고, 실제 Api.js를 호출한다.
  • Playwright로 실제 크롬에서 신청 → 제출 → 선발 → 심사 → 시상까지 통과시킨다.
  • 부하 시험: 100명 동시 열람, 25팀 동시 생성, 75명 동시 합류.
  • 운영 점검 스크립트: 배포된 주소의 canonical·og 태그, 버전 일치, 관리자 코드 미노출.

11. 비개발자 교수를 위한 7가지 설계 원칙

  1. 제약을 먼저 말하라. 계정·정원·필수 문구·보유 기간을 첫 프롬프트에 넣어라. 중간에 바꾸면 마이그레이션이 된다.
  2. 상태를 한 곳에 모아라. 원본이 두 곳에 있으면 반드시 갈라진다. 시트는 사본, 원본은 하나.
  3. 읽기와 쓰기를 분리하라. 읽기는 캐시하고, 쓰기는 한 경로로 모아라. 성능과 보안이 동시에 좋아진다.
  4. '같다'의 기준을 파일로 만들어라. 공문서는 말로 검수하지 말고 겹쳐서 검수하라.
  5. AI에게 판단을 맡기되 평균과 근거를 남겨라. 한 번의 점수는 의견이고, 세 번의 평균은 데이터다.
  6. 개인정보는 화면이 아니라 서버에서 가려라. 화면에서 숨기는 것은 가린 것이 아니다.
  7. 완료 선언을 믿지 말고 더미로 끝까지 돌려라. "됐습니다"는 가장 비싼 거짓말이다.

12. 에필로그: 물리치료와 코딩의 공통점 — 병목 제거

물리치료사는 통증을 호소하는 부위만 보지 않습니다. 무릎이 아프면 발목의 가동성, 고관절의 회전, 골반의 안정성을 차례로 봅니다. 통증은 움직임의 사슬이 끊긴 지점에서 나타나고, 몸은 그 틈을 다른 곳의 보상작용으로 메웁니다. 치료는 그 사슬에서 막힌 곳을 찾아 다시 움직이게 하는 일입니다. DNS(Dynamic Neuromuscular Stabilization)를 가르칠 때 제가 학생들에게 늘 하는 말도 같습니다.

"막힌 곳을 억지로 미는 게 아니라, 왜 거기가 막혔는지를 찾아라."

이 시스템을 만들면서 그 문장을 코드에 그대로 적용했습니다.

  • 구글 시트의 3초 락은 관절의 가동 제한이었습니다. 그 주변(재시도, 대기열)이 과부하되며 전체가 느려졌습니다. 락 구간을 0.1초로 줄이자 보상작용이 사라졌습니다.
  • HWPX/PDF 불일치는 정렬의 문제였습니다. 서로 다른 엔진이 같은 자세를 만들 수 없듯, 서로 다른 렌더러는 같은 문서를 만들 수 없습니다. 원본 엔진을 쓰거나, 규칙을 그대로 옮겨야 했습니다.
  • 42회 AI 심사는 평가의 재현성 문제였습니다. 한 번의 측정으로 치료 계획을 세우지 않듯, 한 번의 채점으로 시상하지 않았습니다.

그리고 가장 큰 깨달음은 이것입니다. 시스템이 느려지는 이유는 대개 코드가 나빠서가 아니라 한 사람이 병목이 되어서입니다. 엑셀을 붙잡은 운영자, 신청서를 손으로 고치는 조교, 코드를 눈으로 읽는 심사위원. 바이브 코딩이 실제로 한 일은 그 사람들을 대체한 것이 아니라, 사람이 병목이 아니어도 되게 만든 것입니다.

행사 마지막 날, 저는 무대 뒤에서 노트북 한 대로 시상 결과를 공개했습니다. 14팀의 점수는 이미 계산되어 있었고, 저는 버튼 하나를 눌렀습니다. 그때 제가 한 일은 코딩이 아니라 버튼을 누르는 일이었고, 그 버튼을 만들 수 있었던 이유는 제가 물리치료과 교수라서가 아니라, 병목이 어디인지 20년 동안 환자에게 물어봤기 때문입니다.

당신의 현장에도 병목이 있습니다. 그것을 정의할 수 있다면, 코딩은 이제 가장 쉬운 부분입니다.
