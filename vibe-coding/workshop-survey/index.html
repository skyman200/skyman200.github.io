[바이브코딩 12편] 구글폼 대신 직접 만든 워크숍 만족도 조사 — 5시간·16커밋·2,916줄

만족도 조사는 폼으로 받고 엑셀로 세는 것이 기본값이다. 그 기본값을 버리고 설문 화면과 실시간 분석 대시보드, PDF·HWPX 보고서, AI 종합분석까지 한 페이지에 담았다. 프레임워크는 없고, 서버는 Supabase 무료 티어 하나다. 2026년 8월 5일 오후 다섯 시간 동안 올린 16개 커밋의 기록.

이번 편은 행사 하나를 위해 만든 웹앱의 기록입니다. 대상은 동의과학대학교 교강사 워크숍 만족도 조사이고, 저장소는 공개된 skyman200/workshop-survey입니다. 첫 커밋은 2026년 8월 5일 13시 38분, 마지막 커밋은 같은 날 18시 29분입니다. 4시간 51분, 커밋 16개. 아래 수치는 그 저장소의 코드 줄 수(wc -l), 스키마, 커밋 로그에서 직접 센 것만 적었습니다. 저장소에 없는 응답자 규모나 운영 성과는 쓰지 않았습니다.

1워크숍은 끝나고, 분석은 다음 주에 온다

만족도 조사의 병목은 응답을 받는 데 있지 않습니다. 응답을 해석하는 데 있습니다. 폼 링크를 뿌리면 응답은 금방 쌓이지만, 그다음에 남는 일은 이렇습니다. 문항 10개를 문항별로 평균 내고, 영역 4개로 묶어 비교하고, 전임·겸임·강사 직급별로 갈라 보고, 31개 학과를 순위로 세우고, 자유의견 수십 건을 읽어 키워드로 묶습니다. 이걸 시트에서 손으로 하면 워크숍이 끝난 다음 주에야 한 장짜리 표가 나옵니다.

그런데 워크숍 주최자가 결과를 가장 필요로 하는 시점은 행사가 끝난 그날입니다. 다음 학기 프로그램을 정하는 회의가 바로 다음 주에 잡혀 있기 때문입니다. 그래서 이번에는 조건을 먼저 정했습니다.

  • 응답자는 로그인 없이 2분. 이름을 받지 않고, 소속 학과와 직급만 고른다. 앱 설치도, 회원가입도 없다.
  • 결과는 같은 날 보여준다. 응답이 들어오는 즉시 대시보드가 다시 그려진다. 다음 주에 집계하는 일이 없다.
  • 학과별로는 자기 학과만 본다. 31개 학과 결과를 아무나 열람할 수 있으면 안 된다. 관리자 PIN으로 나눈다.
  • 결과는 학교 문서로 나온다. 화면 캡처가 아니라 PDF와 한글(HWPX) 파일. 교무·행정으로 넘어가는 문서이기 때문이다.

이 네 줄이 이 글의 나머지 전부입니다. 어떤 기능을 넣었는지가 아니라, 이 조건을 지키려고 만든 장치들 — 통계 엔진, RLS 정책, PIN RPC, 서버 프록시 — 의 이야기입니다.

3의존성 0 — 차트 8종을 직접 그린 이유

이 앱에는 차트 라이브러리가 없습니다. js/charts.js 320줄이 SVG를 직접 만듭니다. 게이지, 수평·수직 막대, 레이더, 리커트 100% 누적, 도넛, 그룹 막대, 추이선 — 여덟 종입니다. 각 함수는 컨테이너와 옵션을 받아 document.createElementNS로 도형을 그리고, 좌표는 극좌표 변환과 호 경로 계산 몇 줄로 끝냅니다.

이유는 취향이 아니라 배포 환경입니다. 이 앱은 교내망과 모바일 브라우저에서 열리고, 링크는 메신저로 공유됩니다. 차트 라이브러리를 CDN에서 불러오는 구조라면 CDN 하나가 막히는 순간 화면 전체가 빈 카드가 됩니다. 실제로 이 저장소는 나중에 같은 문제를 한 번 겪습니다 — 학교망이 Vercel을 막아 HWPX 변환이 실패한 일입니다(10절). 그때 배운 것을 차트에 미리 적용해 둔 셈입니다.

// js/dashboard.js — 종합 게이지 한 줄
Charts.gauge(summaryCard.querySelector("#heroGauge"),
  { value: R1(s.overallScore100), max: 100, label: "종합 만족도", unit: "점" });

직접 그리면 얻는 것이 하나 더 있습니다. 색을 데이터에 맞출 수 있습니다. 이 앱의 5점 척도는 브릭(#a8473a) · 오커(#cd9350) · 스톤(#bdb7a8) · 세이지(#7a9f88) · 파인(#3c6350) 다섯 색으로 고정되어 있고, 평균 점수에 따라 색이 달라지는 규칙(scoreColor)도 코드 안에 있습니다. 라이브러리의 기본 팔레트를 쓰면 이 규칙을 매번 옵션으로 덮어써야 합니다.

4통계는 서버가 아니라 화면에서 계산한다

js/data.js 507줄에 문항 정의, 저장소, 통계 엔진, 데모 데이터가 모두 들어 있습니다. 중심은 compute() 한 함수입니다. 응답 배열과 문항 배열을 받아 다음을 한 번에 계산합니다.

  • 문항별 — 평균, 표준편차, 5단 분포, 긍정응답률(top-box: 4~5점), 부정응답률(bottom-box: 1~2점), 100점 환산
  • 영역별 — 4개 영역의 평균과 100점 환산
  • 직급별 — 전임·겸임·강사 각각의 평균과 응답 수
  • 학과별 — 31개 학과 평균을 내림차순 정렬
  • 전체 분포 — 다섯 선택지에 몇 명이 답했는지
  • 재참여 의향 — 10번 문항을 NPS처럼 계산(추천자 − 비추천자)
  • 강점·개선점 — 문항 평균 상위 3개와 하위 3개
  • 자유의견 — 최신순 정렬 + 불용어를 뺀 키워드 빈도

이 계산을 브라우저에서 하는 이유는 세 가지입니다. 첫째, 응답이 수십 건 규모에서 서버 집계 함수를 따로 두는 것은 배보다 배꼽이 큽니다. 둘째, 필터를 바꿀 때마다 데이터베이스를 다시 부르지 않으므로 무료 티어의 호출과 대역폭이 거의 들지 않습니다. 셋째, 계산식이 코드에 그대로 보이므로 "이 100점은 어떻게 나온 숫자인가"를 나중에 확인할 수 있습니다. 100점 환산은 5점 평균을 20배 한 값이고, 등급은 90·80·70·60에서 잘립니다. 대시보드 맨 위의 KPI 여섯 칸도 같은 값에서 나옵니다 — 총 응답 수, 종합 만족도(100점), 평균 점수, 긍정 응답률, 재참여 의향, 자유의견 건수.

한계도 적어 둡니다. 브라우저가 원자료를 받아 계산하는 구조는 응답이 수천 건을 넘으면 병목이 됩니다. 그 규모에서는 Postgres 집계 뷰나 RPC로 계산을 서버로 옮겨야 합니다. 지금 구조는 교내 워크숍 규모를 전제로 한 선택입니다.

5백엔드는 표 하나, 정책 두 줄

스키마 파일은 57줄입니다. 응답 테이블 하나에 컬럼 8개이고, 문항 응답은 answers 한 칸에 JSON으로 들어갑니다.

create table if not exists public.responses (
  id          uuid        primary key default gen_random_uuid(),
  created_at  timestamptz not null    default now(),
  participant text        default '',
  department  text        default '미기재',
  position    text        default '전임',
  session     text        default '',
  answers     jsonb       not null,          -- {"1":4,"2":5,...,"10":4}
  feedback    text        default ''
);

문항을 컬럼으로 펼치지 않은 이유는 기능 때문입니다. 이 앱은 학과마다 설문을 조금씩 바꿀 수 있습니다. 제목과 안내문을 고치고, 표준 10문항 중 일부를 빼거나 순서를 바꾸고, 그 학과만의 문항을 추가할 수 있습니다. 문항이 학과별로 달라지면 컬럼 구조로는 감당이 안 됩니다. JSON 한 칸이면 문항이 몇 개든 같은 표에 들어갑니다.

권한은 RLS 두 줄로 정합니다. 익명 사용자에게 INSERT와 SELECT만 허용하고 UPDATE·DELETE는 막습니다. 응답을 넣고 읽는 것이 이 앱의 전부이므로, 고치고 지우는 권한은 애초에 주지 않았습니다.

그리고 클라우드가 없어도 동작합니다. config.js의 주소와 키가 비어 있으면 앱은 브라우저 저장소만 쓰는 로컬(키오스크) 모드로 떨어집니다. 행사장에 노트북 한 대를 두고 그 자리에서 응답을 받는 방식에는 이쪽이 오히려 맞습니다. 화면 오른쪽 위의 작은 표식이 지금 어느 모드인지 알려 줍니다 — '로컬' 또는 '클라우드'.

6PIN은 응답 테이블에 두지 않는다

처음 스키마는 익명에게 SELECT를 열어 두었습니다. 대시보드를 보려면 응답을 읽어야 했기 때문입니다. 그런데 그 상태에서는 링크를 아는 사람이면 누구나 전체 응답을 읽을 수 있습니다. 학과별로 결과를 나누려던 조건과 정면으로 부딪힙니다.

그래서 같은 날 오후에 접근 구조를 바꿨습니다. 익명의 responses 직접 조회를 막고, 학과와 PIN을 받는 dept_login RPC 하나만 남겼습니다. PIN은 dept_pins 테이블에 bcrypt 해시로 저장되고, 그 테이블에는 익명 정책이 아예 없습니다. RPC는 security definer로 PIN을 검증한 뒤, 맞을 때만 해당 학과의 응답을 돌려줍니다. 대시보드 앞에는 PIN 입력 화면이 서고, 전체 통합 분석은 마스터 PIN이 있어야 열립니다.

시드(실제 PIN 값)는 저장소에 넣지 않았습니다. 스키마 주석에 그렇게 적어 두고, 관리자용 PIN 파일은 .gitignore에 걸었습니다.

# 관리자 PIN 등 비밀 — 공개 저장소에 절대 커밋 금지
*관리자PIN*
*마스터PIN*
*PIN*.xlsx
*PIN*.csv

저장소의 마지막 커밋이 그 .gitignore였습니다. 관리자 PIN을 엑셀·CSV로 관리하던 시점에, 그런 파일이 저장소에 섞여 들어가지 않도록 이름 패턴으로 막은 것입니다. 비밀은 코드가 아니라 파일 이름에서 새어 나옵니다.

정직하게 적어 둘 것. PIN을 여러 번 넣어 보는 무차별 대입을 막는 장치는 코드에 없습니다. 브라우저가 PIN 문자열을 들고 RPC를 호출하므로, PIN은 TLS 구간을 지나 서버까지 갑니다. 교내 소규모 행사에서 학과 결과를 서로 가리는 수준의 장치이고, 외부에 공개되는 서비스의 인증으로는 부족합니다. 그 용도라면 Supabase Auth와 사용자별 정책으로 가야 합니다.

7AI는 브라우저에서 부르지 않는다

대시보드에는 'AI 종합분석' 버튼이 있습니다. 누르면 통계가 문장이 되어 돌아옵니다. 이 호출은 브라우저가 AI 제공자에게 직접 가지 않습니다. Supabase Edge Function 한 개(ai-analyze, 97줄)를 거칩니다.

이유는 단순합니다. 브라우저 번들에 API 키를 넣으면 그 키는 공개된 것입니다. 이 사이트는 저장소도 공개하고 anon 키도 공개하지만, anon 키는 RLS가 권한을 제한하는 공개용 키입니다. AI 게이트웨이 키는 그런 성격이 아니라서 서버 시크릿(Deno.env)에만 둡니다. 함수는 90초에 타임아웃을 걸고, 응답은 1,600 토큰으로 자릅니다.

프롬프트도 서버가 고정합니다. 화면에서 문장을 바꿀 수 없습니다. 규칙은 두 줄로 요약됩니다.

위 통계만 근거로 대학 워크숍 만족도 분석 보고를 한국어로 작성하라.

      과장·상투어 금지. 간결한 개조식.

프롬프트에 실어 보내는 것도 원자료가 아니라 집계값입니다. 응답자 수, 100점 환산, 긍정·부정 비율, 문항별 평균과 긍정률, 영역별 평균, 직급별 평균, 재참여 NPS, 강점·개선점 상위 3개, 그리고 자유의견은 최대 15건만 140자로 잘라 넣습니다. 이름과 소속은 보내지 않습니다. 응답 원문을 통째로 넘기면 개인을 특정할 수 있는 문장이 그대로 외부로 나가기 때문입니다.

이 구조의 값은 결과물이 아니라 실패 방식에 있습니다. 키가 없으면 함수는 "서버에 시크릿이 설정되지 않았습니다"라고 500을 돌려주고, 게이트웨이가 실패하면 상태 코드와 본문 앞부분을 잘라 502로 돌려줍니다. 화면에는 그 문장이 그대로 뜹니다. AI가 안 되면 AI 없이 PDF를 만들면 되고, 그 사실을 사용자가 알아야 합니다.

8보고서는 화면에서 끝난다

분석이 끝나면 세 가지로 내보냅니다. PDF, HWPX, 그리고 화면 자체입니다.

PDF는 report.js 264줄이 만드는 격식 보고서를 그대로 인쇄합니다. 문항마다 문항 제시 → 응답 분포 → 통계 → 해석 순으로 서술이 붙고, 종합 막대와 표가 따라붙습니다. 해석 문장은 규칙으로 생성됩니다 — 긍정률 85% 이상이면 "응답자 대다수가 긍정적으로 평가했다", 70% 이상이면 "대체로 긍정적이나 일부 개선 여지가 있다", 부정 응답이 8%를 넘으면 그 사실을 덧붙입니다. 라이브러리(html2canvas 1.4.1, jsPDF 2.5.2)는 버튼을 누를 때 CDN에서 불러옵니다. 대시보드를 보기만 하는 사람에게 400KB를 먼저 내려보내지 않기 위해서입니다.

HWPX가 이 앱의 진짜 목적지입니다. 학교에서 도는 보고는 한글 문서이기 때문입니다. 브라우저가 보고서를 Markdown으로 만들고, 외부 변환 엔드포인트에 POST해 HWPX 파일을 받습니다. 문제는 그 엔드포인트가 학교망에서 막힌다는 것이었습니다. 그래서 순서를 바꿨습니다 — Cloudflare Worker 프록시를 먼저 시도하고, 안 되면 Vercel로 직행하고, 둘 다 실패하면 Markdown 파일을 내려줍니다. 세 단계 중 어디서 멈춰도 사용자는 손에 파일 하나를 들고 있습니다.

9AI 슬롭을 걷어낸 커밋 하나

16개 커밋 중 성격이 가장 다른 것은 디자인 전면 개편입니다. 커밋 메시지는 이렇습니다 — "디자인 전면 개편: 에디토리얼 스타일로 AI 슬롭 제거 (세리프 제목·종이 배경·네이비 단색·이모지/그라데이션 제거·저채도 데이터 색)".

바뀐 것은 CSS 변수 몇 줄이지만 효과는 화면 전체입니다. 배경은 종이색(#f4f2ec), 카드는 흰색, 글자는 잉크색(#1b1a17), 액센트는 딥 네이비(#21324b) 하나. 모서리 반경은 3px, 그림자는 없고 헤어라인 보더로 구분합니다. 데이터 색도 채도를 낮춰 다섯 단계로 고정했습니다. 그라데이션과 이모지는 쓰지 않습니다.

이유가 있습니다. 만족도 조사 결과는 결국 교무·행정 문서로 넘어가는 숫자입니다. 화면이 화려하면 숫자가 가벼워 보이고, "이건 우리가 만든 내부 도구"라는 인상이 붙습니다. 논문·보고서처럼 보이는 화면은 반대 효과를 냅니다. 같은 이유로 링크 미리보기 이미지(OG)도 대시보드형 리포트 디자인으로 다시 만들었습니다 — KPI·게이지·레이더·도넛이 들어간 1,200×630 카드 하나입니다.

조사 결과의 신뢰는 숫자의 정확도에서만 오지 않는다. 그 숫자가 놓인 종이의 태도에서도 온다.

판단 기준은 3편에서 정리한 AI 슬롭 9단계 하네스와 같습니다. 보라색 네온, 이모지 남발, 어긋난 마진을 걷어내고 정보 위계만 남기는 일입니다.

10실제로 터진 것들

다섯 시간짜리 작업에서도 막히는 자리는 있었습니다. 커밋 메시지에 그대로 남아 있는 것들입니다.

01 응답이 0건이면 분석 화면에 들어갈 수 없었다

빈 대시보드는 "응답이 없습니다"만 보여 주고 끝났습니다. 그런데 학과별 설문을 미리 세팅하려면 응답이 0건인 상태에서 편집기에 들어가야 합니다. 결국 빈 화면에 편집기 버튼을 붙였습니다. 기능 하나를 더 만든 것이 아니라, 아무것도 없는 상태를 정상 상태로 취급한 커밋입니다.

02 데모 데이터가 클라우드에서 안 불러와졌다

화면을 보여 주려고 만든 46건짜리 데모 데이터가 클라우드 모드에서 동작하지 않았습니다. 로컬 저장소에만 넣고 있었기 때문입니다. 데모 데이터도 진짜 응답과 같은 경로로 넣도록 고쳤습니다. 시연용 경로와 실제 경로가 다르면, 시연에서 통과한 것이 실제에서 터집니다.

03 PDF가 잘리고, HWPX는 PDF와 레이아웃이 달랐다

페이지 경계에서 표가 잘렸고, HWPX로 변환한 문서는 PDF와 줄이 어긋났습니다. 두 파일이 같은 문서처럼 보여야 하는데, 실제로는 서로 다른 문서였습니다. 잘림을 고치고, HWPX 변환에 넘기는 Markdown을 PDF 레이아웃에 맞춰 다시 썼습니다. 같은 내용을 두 형식으로 낸다면, 형식이 아니라 원본을 하나로 만들어야 합니다.

04 학교망에서 Vercel이 막혔다

HWPX 변환 엔드포인트가 교내망에서 응답하지 않았습니다. 도메인을 바꾸는 대신 경로를 하나 더 얹었습니다 — Cloudflare Worker가 같은 요청을 대신 보내는 프록시입니다. 지금은 프록시를 먼저 시도하고, 실패하면 Vercel로 직행합니다. 사내망·학교망은 인터넷과 다른 나라입니다.

05 만든 기능을 지웠다 — 회차

처음에는 회차(1차·2차)를 골라 응답을 쌓고 추이선을 그리는 구조였습니다. 그런데 이 행사는 2026학년도 2학기 단일 행사였습니다. 회차 선택 UI와 대시보드의 회차 필터·추이선을 지웠습니다. 다만 통계 엔진은 회차 데이터를 버리지 않았습니다 — 응답에 회차가 2개 이상 쌓이면 요약 문장이 흐름을 말하도록 남겨 두었습니다. 화면에서 지우는 것과 데이터 구조에서 지우는 것은 다른 일입니다.

06 PIN 명단이 커밋될 자리

관리자 PIN을 엑셀·CSV로 다루고 있었습니다. 커밋 한 번이면 31개 학과의 관리자 PIN이 공개 저장소에 올라갈 수 있는 자리였습니다. .gitignore에 파일 이름 패턴을 걸어 막았고, 그 커밋이 이 저장소의 마지막이 되었습니다.

07 외장 볼륨의 ._ 파일

작업 폴더를 외장 볼륨으로 옮긴 뒤 macOS의 ._* 메타 파일이 저장소에 섞여 들어왔습니다. 무시 규칙 한 줄로 정리했습니다. 사소해 보이지만, 이런 파일이 쌓이면 배포 산출물에 섞여 올라갑니다.

11Q&A

Q1.구글폼으로 받으면 되는데 왜 직접 만들었나요?

폼은 응답을 모으는 데는 충분하지만, 문항별 평균·영역 비교·직급별 차이·학과별 순위를 보려면 결국 시트에서 손으로 세야 합니다. 이 앱은 집계가 화면에서 즉시 끝나고, 학과별로는 자기 학과 결과만 보이고, 결과가 PDF·HWPX로 바로 나옵니다. 이 세 가지가 폼 도구의 기본 기능 밖에 있습니다.

Q2.anon 키가 코드에 그대로 있는데 안전한가요?

그 키는 설계상 공개되는 키이고, 권한은 RLS가 정합니다. 익명에게는 INSERT와 SELECT만 허용하고 UPDATE·DELETE는 막았습니다. 이후 익명의 직접 조회를 차단하고, bcrypt PIN을 검증하는 dept_login RPC로만 해당 학과 응답이 나가게 바꿨습니다. PIN 명단과 시드는 저장소에 없습니다.

Q3.응답이 수천 건이 되면 버티나요?

지금은 브라우저가 원자료를 받아 계산합니다. 교내 워크숍 규모에서는 가장 단순하고 무료 티어 호출도 아끼는 방식입니다. 수천 건을 넘으면 원자료 전송과 클라이언트 계산이 병목이 되므로, Postgres 집계 뷰나 RPC로 계산을 서버로 옮겨야 합니다.

Q4.다른 학교나 행사에서도 쓸 수 있나요?

쓸 수 있습니다. 저장소가 공개되어 있고, Supabase 프로젝트를 하나 만들어 스키마를 실행한 뒤 config.js의 주소와 anon 키만 채우면 같은 구성이 됩니다. 키가 비어 있으면 클라우드 없이 브라우저에만 저장하는 로컬 모드로 동작합니다. 문항은 학과별로 제목·안내문·사용 여부·순서를 바꾸고 커스텀 문항을 더할 수 있습니다.

12에필로그 — 다섯 시간이 남긴 것

이 앱은 자랑할 만한 규모가 아닙니다. 코드 2,916줄, 화면 두 개, 다섯 시간입니다. 앞선 편들의 시스템처럼 몇 주를 쓰지도 않았고, 93개 커밋이 쌓이지도 않았습니다. 대신 행사가 끝난 그날 결과가 나옵니다. 다음 학기 프로그램을 정하는 자리에 "가장 낮은 평가를 받은 항목이 무엇이고, 어느 직급·어느 학과에서 갈렸는지"를 숫자와 함께 들고 갈 수 있다는 것이 이 도구의 목적입니다. 실제 응답 수치와 운영 성과는 저장소에 없으므로 이 글에는 적지 않았습니다.

그리고 이 구조는 한 번 만들면 다음 행사에도 그대로 씁니다. 문항이 바뀌면 편집기에서 고치고, 학과가 바뀌면 목록에서 고르고, 새 학기에는 회차를 다시 켜면 됩니다. 행사마다 폼을 새로 만들고 엑셀을 새로 짜는 일이 사라지는 것이 다섯 시간의 값입니다.

좋은 내부 도구는 눈에 띄지 않는다. 행사가 끝난 날, 아무도 집계를 위해 야근하지 않는 것으로 존재를 증명한다.
