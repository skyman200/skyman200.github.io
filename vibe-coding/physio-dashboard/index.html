[바이브코딩 21편] 태그 16개, 8시간 53분 — 데스크톱 앱을 만들었다가 스스로 부순 30커밋

물리치료학과 10개 화면짜리 협업 캘린더를 데스크톱 앱으로 배포하려 했습니다. Electron을 버리고 Tauri로 갔고, 코드 서명과 자동 업데이트를 붙였고, 8시간 53분 만에 16번째 태그에서 그 기능들을 지웠습니다. 이 글은 그 하룻밤의 계측입니다 — 그리고 첫 커밋이 전체 삽입의 94.2%라는, 제가 지금까지 쓴 글 중 가장 불편한 숫자 하나.

작성자 김강훈 교수 (동의과학대학교 물리치료과 교수·학과장 / DIT AI 허브센터 팀장)

이 연재의 스물한 번째 편입니다. 지난 20편에서 저는 “문서를 만들지 않고 완성본을 수술했다”고 썼습니다. 이번 편의 답은 더 불편합니다. 완성본은 제가 만들지 않았습니다. 저장소 skyman200/dphysio의 첫 커밋(7ffc106, 2025-12-27 10:58)에는 이미 267개 파일과 56,214줄이 들어 있었고, 그날 밤 제가 한 일은 그 위에 3,451줄을 더하고 2,113줄을 지우는 것이었습니다.

그런데 그 3,451줄 중 절반은 기능이 아니라 포장이었습니다. Electron 창을 Tauri 창으로 바꾸고, 코드 서명을 붙이고, macOS arm64·x64와 Windows 설치 파일을 GitHub 릴리스에 올리는 일. 그리고 그 포장은 실패했습니다. 이 글은 실패한 포장을 어떻게 회수했는지, 그 뒤에 남은 진짜 기능이 무엇이었는지, 그리고 그 기능이 지금 라이브에서 어떤 상태인지를 순서대로 적습니다.

이 글에서 쓰는 “실측”의 뜻 — 공개 저장소 skyman200/dphysio를 클론해 git log·git ls-files·git tag·파일 계수로 센 값, 각 파일을 직접 읽고 문자열을 센 값입니다. 라이브 상태는 이 글을 쓰는 자리에서 curl과 원격 브라우저로 직접 확인했습니다(홈 200, 7,736바이트 / 배포 번들 6개 1,725,578바이트). 저장소에 테스트가 0개이고 이 작업 환경에는 Node.js가 없어 npm run build·tsc는 실행하지 못했습니다. 그 사실은 본문에 그대로 적었습니다. 교내 인원의 이름·일정 같은 실제 데이터와 Firebase 키·R2 자격증명은 이 글에 쓰지 않습니다.

04첫 커밋 — 267파일 56,214줄, 전체의 94.2%

첫 커밋을 열어 보면 이렇습니다. 화면·훅·컴포넌트·Cloud Functions·보안 규칙·CI 워크플로·Electron 셸·Tauri 설정이 한 번에 들어 있습니다. README.md 73줄은 “Welcome to your Lovable project”로 시작하는 도구의 기본 문서 그대로이고, package.json에는 lovable-tagger가 들어 있습니다. 즉 이 웹앱 본체는 바이브코딩 도구(Lovable)에서 생성된 코드베이스입니다.

반면 같은 커밋의 GUIDELINES.md는 755줄입니다. DRY·KISS·YAGNI·SOLID에 시작해 “파일 200줄 초과 금지”, “N+1 쿼리 금지”, “전체 컬렉션 구독 금지”, “any 타입 절대 금지”, Firestore 소유자 체크 규칙, API 키 노출 금지, “절대 하지 말 것(Red Flags)”까지 — AI 에이전트에게 주는 계약서입니다. README 73줄과 GUIDELINES 755줄의 이 10배 차이가 이 저장소의 성격을 가장 잘 보여 줍니다. 설명서는 템플릿이고, 진짜 설계도는 지침서입니다.

숫자를 정확히 — 첫 커밋 삽입 56,214줄 ÷ 전체 삽입 59,665줄 = 94.2%. 남은 29커밋의 삽입은 3,451줄, 삭제는 2,113줄입니다. 이 저장소에서 새로 만들어진 파일은 9개뿐입니다(달력 보기 전환·주간 목록·일정 목록·휠 선택기·구독 버튼·회의 폼·Apple 날짜 선택기·Tauri 스텁·capability), 삭제 1개(bun.lockb). 나머지 커밋은 전부 기존 파일을 고친 것입니다.

저는 이 사실을 변명하지 않겠습니다. 이 연재가 재는 것은 “내가 몇 줄을 썼나”가 아니라 “무엇이 어려웠고 무엇이 틀렸나”이기 때문입니다. 다만 독자가 같은 방식으로 앱을 만들 계획이라면 이 비율은 반드시 알아야 합니다. AI가 만든 5만 6천 줄은 그대로 믿을 수 있는 자산이 아닙니다. 그 위에 얹은 3,451줄이 무엇을 고쳤는지가 이 글의 나머지입니다.

05첫 결정 — 웹앱을 데스크톱에 넣는다 (Electron에서 Tauri로)

이 앱이 데스크톱이어야 했던 이유는 단순합니다. 교수들이 하루 종일 브라우저 탭 20개 사이에서 이 캘린더를 잊고 산다는 것. 트레이에 상주하고 로그인과 함께 켜지는 창이 필요했습니다. 그래서 두 개의 셸을 같은 저장소에 넣었습니다.

Electron 셸(electron/main.cjs 210줄)은 성실합니다. V8 힙을 8GB로 올려 고해상도 PDF·이미지 처리 시 크래시를 막고(--max-old-space-size=8192), 로그인 시 자동 시작하면서 --hidden으로 트레이에만 뜨고, 창을 닫으면 종료하지 않고 숨기며, 단일 인스턴스 잠금과 트레이 메뉴(“열기”/“완전히 종료”)까지 갖췄습니다.

Tauri 셸(src-tauri/src/main.rs 75줄)이 같은 일을 Rust로 다시 합니다. 트레이·자동시작(tauri-plugin-autostart)·창 숨김. 바이너리는 훨씬 작고, macOS·Windows 설치 파일을 한 워크플로에서 뽑을 수 있습니다.

// src-tauri/src/main.rs (75줄 중 핵심)
.on_window_event(|window, event| {
    if let WindowEvent::CloseRequested { api, .. } = event {
        let _ = window.hide();
        api.prevent_close();
    }
})

여기까지는 좋았습니다. 문제는 그다음 — 사용자 기기에 설치되는 앱은 서명이 없으면 신뢰되지 않고, 자동 업데이트는 서명 키 쌍이 맞아야만 동작한다는 것이었습니다.

08껍데기에 남은 것 — 보안 설정을 그대로 적는다

이 대목은 자랑이 아니라 기록입니다. 두 셸의 보안 설정은 편의를 위해 열어 둔 값이고, 그대로 남아 있습니다.

위치설정의미

정직하게 말하면, 이 셸은 브라우저입니다. 원격 웹앱을 로드하는 창에서 nodeIntegration을 켜 두는 것은 웹 쪽 스크립트 하나가 로컬 파일에 닿을 수 있다는 뜻입니다. 다행히 v2.0.0 이후 실제로 배포되는 셸은 Tauri(권한 4개, Node 접근 없음)이고 Electron은 저장소에 남은 이전 경로입니다. 그래도 electron-builder 설정이 package.json에 그대로 살아 있어서, 누군가 npm run electron:build를 누르면 그 설정으로 빌드됩니다. 지우지 않은 것은 제 판단 실수입니다.

10자연어 일정 — 로컬 파서 284줄이 먼저다

이 앱에서 제가 가장 애정하는 부분은 화면이 아니라 src/utils/scheduleParser.ts 284줄입니다. “내일 오후 3시 학과 회의” 같은 문장을 날짜·시간·장소로 바꾸는 코드입니다.

구조는 규칙 먼저, 라이브러리는 보조입니다. 한국어 시간 표현은 정규식 7개로 잡고, 애매한 표현만 chrono-node에 넘깁니다.

const PATTERNS = {
  DATE_ABSOLUTE: /(\d{1,2})\s*[월./]\s*(\d{1,2})(?:\s*일)?/,        // 10월 5일, 10.5
  DATE_RELATIVE: /(오늘|내일|모레|글피)/,                             // 글피까지 있다
  DATE_WEEKLY:   /(이번|다음|다다음|담)\s*주\s*([월화수목금토일])요일/,  // 담주 화요일
  TIME_RANGE:    /(오전|오후|아침|점심|저녁|밤)?\s*(\d{1,2})(?:\s*시|:(\d{2}))?
                  \s*(?:부터|~|-)\s*(오전|오후|아침|점심|저녁|밤)?\s*(\d{1,2}).../,
  TIME_MERIDIEM: /(오전|오후|아침|점심|저녁|밤)\s*(\d{1,2})시(?:\s*(\d{1,2})분)?/,
  TIME_24HR:     /(\d{1,2}):(\d{2})/,
  TIME_SIMPLE:   /(\d{1,2})시(?:\s*(\d{1,2})분)?/,
};

재미있는 것은 숫자만 말했을 때의 추론입니다. 오전·오후를 말하지 않으면 inferHour()가 7~11시는 오전, 1~6시는 오후로 읽습니다. “3시 회의”는 오후 3시, “10시 회의”는 오전 10시. 사람이 실제로 그렇게 말하기 때문입니다. “점심 12시”는 12시, “밤 2시”는 새벽 2시.

그리고 결과에는 신뢰도가 붙습니다. 화면은 confidence > 0.4일 때만 미리보기를 띄우고, 그 아래면 저장하지 않고 이렇게 답합니다.

“📅 날짜와 시간을 좀 더 정확히 말씀해 주세요 (예: ‘내일 3시’) — 현재 로컬 분석 모드입니다.”실제 화면 문구

11그리고 AI를 껐다 — 함수 6개 중 1개가 미사용

이 앱에는 AI 일정 파싱이 두 겹으로 들어 있습니다. 서버에는 parseScheduleWithAI가 있고, Gemini→OpenAI→Grok 순서로 폴백하며 키가 있는지 로그로 남기고, 셋 다 실패하면 “모든 AI 모델이 응답하지 않습니다”로 끝납니다. 클라이언트에는 aiApi.ts가 있습니다.

그런데 화면의 함수는 이렇게 시작합니다.

aiApi를 import하는 컴포넌트는 0개입니다. 즉 서버 함수와 API 래퍼는 살아 있지만 아무도 부르지 않습니다. 실제 입력은 10절의 로컬 파서가 혼자 처리합니다.

왜 껐을까요. 제 기록으로는 두 가지입니다. 첫째, 일정 하나를 저장하려고 외부 API를 부르는 지연이 사용자 경험을 망칩니다. 로컬 파서는 즉시 답하고, 틀리면 사용자가 고치면 됩니다. 둘째, 교내 일정 문장에는 사람 이름·과목명·장소가 들어갑니다. 그 문장을 외부 모델로 보내는 순간 데이터 처리 동의 문제가 생깁니다.

그래서 이 앱의 AI 사용은 0회입니다. 이 연재에서 AI를 “덜 쓴” 사례는 처음이 아니라, 16편 자세 분석(외부 API 0회)에서 한 번 있었습니다. 다만 이번엔 만들어 놓고 끈 경우입니다. 코드는 남아 있어서, 필요하면 handleAIParse의 한 줄을 지우면 다시 켜집니다. 끄는 것도 설계라는 말은 이런 뜻입니다.

14그 200줄은 지금 500으로 돌아온다

이 글을 쓰는 자리에서 실제로 호출해 봤습니다. 실패했습니다.

$ curl -s -o /dev/null -w "%{http_code}" \
  "https://us-central1-...cloudfunctions.net/getCalendarFeed?type=department"
500      # 첫 호출
503 503 503   # 이후 3회 재시도 모두 503

$ curl -X POST -d '{"data":{"prompt":"내일 오후 3시 학과 회의"}}' \
  ".../parseScheduleWithAI"
503  "The service you requested is not available yet. Please try again in 30 seconds."

$ curl ".../bogusFunctionName123"
404      # 함수가 없는 이름은 404 — 함수 자체는 배포돼 있다

정리하면 이렇습니다. 함수는 존재하지만 지금 응답하지 않습니다. 그리고 원인은 코드에 하나 있습니다.

getCalendarFeed는 이렇게 조회합니다. events에서 type이 in ['department','professor']이고 start_date 순으로 정렬. Firestore에서 where + orderBy 조합은 복합 인덱스를 요구합니다. 그런데 저장소의 firestore.indexes.json에 정의된 인덱스는 3개이고, 전부 thread_messages·meeting_items용입니다. events 인덱스는 없습니다.

이건 추론입니다 — 500/503의 실제 로그는 제가 볼 수 없습니다. 다만 “복합 인덱스 없음 + where/orderBy 조합”은 Firestore에서 failed-precondition을 내는 전형이고, 저장소에 그 인덱스가 없다는 것은 확인된 사실입니다. 라이브가 500이든 503이든, 이 기능은 배포 시점에 동작이 확인된 적이 없다는 점은 변하지 않습니다.

세 가지 결함을 더 적습니다. ① 인증이 없습니다. 이 피드는 URL만 알면 누구나 학과 일정 제목·설명·장소를 읽습니다(의도일 수 있지만, 그 결정이 문서화돼 있지 않습니다). ② 줄 접지(folding)가 없습니다. iCalendar 표준은 75옥텟을 넘는 줄을 접어야 하는데, 한글 제목은 쉽게 넘습니다. ③ 줄바꿈이 CRLF가 아니라 LF입니다. 아이폰이 받아 주는지는 확인하지 못했습니다 — 함수가 응답하지 않으니까요.

16테스트 0개, 그리고 라우트에 없는 화면 712줄

17이 앱이 남긴 세 문장

01 배포의 병목은 기능이 아니라 서명이다

8시간 12분, 태그 16개 중 기능 태그는 0개였습니다. 설치형 앱을 만드는 사람에게 진짜 관문은 키·인증서·설치 파일 이름입니다. 이 관문을 “나중에”로 미루면, 그 나중이 하루의 절반을 가져갑니다. 반대로 포기할 수 있는 것을 빨리 포기하면 그날 안에 배포가 끝납니다. 제 선택은 후자였습니다.

02 AI를 끄는 것도 기능이다

만들어 둔 AI 파싱을 호출 한 줄로 껐습니다. 대신 로컬 파서 284줄이 “내일 3시”를 즉시 처리하고, 애매하면 저장하지 않고 다시 묻습니다. 일정에는 사람 이름과 장소가 들어가므로 외부로 보내지 않는 것이 이 앱에서는 옳았습니다. AI를 켜는 판단보다 끌 줄 아는 판단이 어렵습니다.

03 마지막 커밋이 가장 예쁘고, 가장 안 쓰인다

00:31의 200줄은 이 앱에서 가장 야심 찬 코드였습니다. 그런데 배포 번들에 없고, 서버는 500을 돌려줍니다. 기능은 커밋이 아니라 “사용자가 본 화면”으로 완성됩니다. 그래서 이 연재는 앞으로 “몇 줄을 썼나”보다 “라이브에서 무엇이 되나”를 먼저 재려고 합니다.

18한계 — 이 글이 확인하지 못한 것

이 연재의 규칙대로, 확인한 것과 확인하지 못한 것을 나눠 적습니다.

  • 빌드·타입 검사 미실행. 이 환경에 Node.js가 없습니다. npm run build, tsc --noEmit을 돌리지 못했으므로 “타입 오류가 없다"고 쓸 수 없습니다.
  • 테스트 0개. 저장소에 테스트 파일이 없어 “무엇이 깨져도 잡아 주는 것”이 없습니다. 이 앱의 정상 동작은 제가 라이브 화면에서 본 범위까지만 확인됐습니다.
  • 함수 5xx의 원인 미확정. 500·503을 재현해 기록했고 복합 인덱스 부재를 확인했지만, 실제 오류 로그는 보지 못했습니다. 원인 서술은 추론입니다.
  • 아이폰 구독 미검증. 함수가 응답하지 않아 .ics를 실제로 받아 본 적이 없습니다. 75옥텟 접지·LF 줄바꿈이 iOS에서 어떻게 처리되는지도 모릅니다.
  • 서명·설치 파일의 실제 동작 미검증. v1.x 설치 파일을 macOS·Windows에 설치해 보지 않았습니다. 릴리스 자산 5개(맥 dmg 2종·exe·앱 tar 2종)의 존재만 확인했습니다.
  • 첫 커밋의 생성 경로. README와 lovable-tagger로 “Lovable에서 생성된 코드베이스”임을 확인했지만, 어떤 프롬프트로 얼마나 걸려 만들어졌는지는 저장소에 없습니다.
  • 사용 기록 없음. 교수들이 이 앱을 실제로 며칠이나 열었는지(활동 로그·세션 컬렉션이 있지만 데이터는 이 글에 싣지 않음)는 확인하지 않았습니다.

19Q&A

Q1Electron도 Tauri도 있는데, 지금 배포본은 무엇인가?

Tauri입니다. Electron은 v2.0.0 이전의 경로이고, 지금은 src-tauri/가 실제 빌드 대상입니다. 다만 package.json에 electron-builder 설정이 남아 있어 둘 다 빌드 가능한 상태입니다. 이 정리는 제가 아직 하지 않았습니다.

Q2자동 업데이트를 포기하면 사용자는 어떻게 최신 버전을 받나?

받을 필요가 없어졌습니다. 창이 웹앱 주소를 로드하므로 웹에 배포하면 다음 실행부터 최신입니다. 대신 앱 자체(트레이·자동시작·아이콘)를 바꾸려면 여전히 새 설치 파일을 배포해야 합니다.

Q3로컬 파서가 AI보다 나은가?

일정 입력에서는 대체로 그렇습니다. 문장 구조가 좁고(날짜·시간·제목·장소), 틀렸을 때 사용자가 즉시 고칠 수 있고, 외부로 나가는 데이터가 없고, 지연이 0에 가깝습니다. 반대로 “다음 주 화요일이 아닌 수요일로 미루고 30분 늘려 줘” 같은 문맥 수정은 로컬 파서가 못 합니다. 그 영역이 생기면 AI를 다시 켤 수 있습니다 — 코드는 남겨 뒀습니다.

Q4같은 방식으로 학과 앱을 만들 계획이면 무엇부터 봐야 하나?

셋입니다. ① 보안 규칙을 먼저 — 이 앱은 규칙 244줄이 컬렉션 16개의 접근을 결정합니다. ② 포장은 마지막에, 하루를 통째로 — 서명·설치 파일은 반나절을 씁니다. 급하면 웹앱+PWA로 두는 편이 낫습니다. ③ 지우는 날을 정하십시오 — 712줄의 죽은 화면처럼, 안 쓰는 코드는 요청받지 않으면 영원히 남습니다.

20에필로그 — 21편을 닫으며

1편에서 저는 “1년에 시스템 22종”이라고 썼습니다. 이번 편은 그중 가장 평범한 앱입니다. 화려한 AI도 없고, 3만 줄짜리 풀스택도 아니고, 심지어 제가 쓴 코드가 6%입니다.

그런데 이 하룻밤이 저에게 가르친 것은 지난 스무 편보다 많습니다. 설치형 앱의 마지막 1킬로미터는 코드가 아니라 서명이라는 것, AI가 만든 코드 위에서 사람이 하는 일은 대부분 지우고 고치는 일이라는 것, 그리고 배포하지 않은 기능은 기능이 아니라는 것.

다음 편에서는 이 앱의 미완을 정리해 보려 합니다 — events 복합 인덱스 하나 넣고, 함수를 다시 배포하고, 죽은 화면 712줄을 지우고, 그다음에 이 캘린더가 교수들의 하루를 몇 분 줄였는지 재는 일. 줄 수가 아니라 사람이 아낀 시간을 세는 것이 이 연재의 원래 목적이니까요.
