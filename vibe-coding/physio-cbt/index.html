Vibe Coding Case 22 · National Exam CBT

[바이브코딩 22편] 보기가 다섯 개가 아니면 저장되지 않는다 — AI 문항을 시험에 넣지 못하게 하는 4종 봇과 109커밋

물리치료 국가시험을 준비하는 학생을 위한 CBT 시스템을 13일 10시간 동안 만들었습니다. 이 글의 주인공은 AI가 만든 문제가 아니라, AI가 만든 문제를 시험에 넣지 못하게 막는 장치입니다. 보기 5개·정답 1개·중복 0을 서버가 강제하고, OCR이 번호를 흘리면 '검수 필요'로 붙잡고, 채점은 산수로 하고 해설만 AI에게 맡겼습니다 — 그리고 테스트 197개는 아직 한 번도 돌리지 못했습니다.

작성자 김강훈 교수 (동의과학대학교 물리치료과 교수·학과장 / DIT AI 허브센터 팀장)

이 연재의 스물두 번째 편입니다. 지난 21편에서 저는 “배포하지 않은 기능은 기능이 아니다”라고 썼습니다. 이번 편은 그 문장의 반대편에서 시작합니다. 저장소 skyman200/physioexam은 109개 커밋·153개 파일·26,293줄이고, 그중 절반 가까운 47개 커밋이 “고치는” 커밋입니다. 만드는 시간보다 막는 시간이 길었던 프로젝트입니다.

왜 막아야 했는지부터 적겠습니다. 물리치료사 국가시험은 5지선다이고, 정답은 하나이고, 문항 번호는 1번부터 끊김 없이 이어집니다. 교과서 PDF에서 문항을 뽑아 쓰는 일은 원래도 오래 걸렸지만, 이제는 AI가 10초 만에 “그럴듯한” 문항 30개를 만들어 줍니다. 문제는 그 30개 중 몇 개가 실제로 시험에 넣을 수 있는 문항인지를 사람이 다시 전수 검사해야 한다는 것입니다. 저는 그 검사를 사람이 아니라 저장 경로에 붙였습니다.

이 글에서 쓰는 “실측”의 뜻 — 비공개 저장소 skyman200/physioexam을 클론해 git log·git ls-files·파일 계수로 센 값과, 각 파일을 직접 읽고 문자열을 센 값입니다. 라이브 상태는 이 글을 쓰는 자리(2026-11-28 16:34 KST)에서 curl로 직접 확인한 HTTP 상태 코드입니다. 이 작업 환경에는 Node.js와 npm이 없어 npm test·npm run build·tsc를 실행하지 못했습니다 — 테스트 197개와 타입 검사 결과는 모릅니다. 저장소가 비공개이고 관리자 콘솔이 로그인 뒤에 있으므로 접속 주소·계정·키·클라우드 리소스 식별자는 이 글에 쓰지 않습니다. 학생 이름·학번·성적 같은 실제 데이터도 쓰지 않았습니다.

01이 시스템이 하는 일 — 교실 밖의 세 개 화면

이름은 국가시험 대비 CBT 시스템(패키지명 cbt-exam-system, 0.1.0). 화면은 세 개입니다. 관리자 콘솔, 응시 화면, 그리고 그 둘이 부르는 API입니다.

테이블 26개는 크게 네 묶음입니다. 시험 운영(exams·exam_sections·exam_attempts·attempt_answers·grading_results·proctor_events·appeals), 문항(questions·question_bank_items·question_options·question_version_history·subjects), 생성 파이프라인(question_generation_jobs·question_generation_runs·source_documents·document_extraction_jobs·document_segments·question_sources·question_import_errors), AI·감시(ai_grading_results·ai_feedback_cache·student_analytics_cache·bot_alerts·security_events·ocr_review_issues).

03중심은 생성이 아니라 거부다 — 문항이 저장되는 다섯 관문

AI에게 문항을 만들게 하는 일은 이 프로젝트에서 가장 쉬운 부분이었습니다. 어려운 것은 저장입니다. 문항 하나가 데이터베이스에 들어가기까지 다섯 개의 관문을 지납니다.

01 프롬프트 — 최상위 JSON 배열만

시스템 프롬프트는 모델에게 마크다운도, 설명문도, {"questions": [...]} 같은 래퍼 객체도 쓰지 말고 최상위 JSON 배열만 돌려달라고 강제합니다. 문항은 정확히 5개 보기(①~⑤)를 가진 단일 정답 객관식과, 모범답안·키워드 부분점수 규칙을 가진 주관식의 혼합이고, 모든 문항에 해설이 붙습니다.

02 스키마 — zod로 한 번 더

응답은 generatedQuestionSchema로 검증합니다. 모델이 JSON을 조금 흘려도 여기서 형태가 잡히고, 형태가 아니면 문항이 아니라 오류 기록(question_import_errors)으로 남습니다. 5월 18일 커밋 “Constrain AI JSON with runtime schemas”가 이 단계를 만든 커밋입니다.

03 데이터 품질 봇 — 저장 자체를 막는다

DataQualityBot이 지문 빈칸, 보기 개수(5개가 아니면 차단), 빈 보기, 정답 키 누락·범위 위반(A~E, ①~⑤, 1~5만 허용), 기존 지문 중복, 같은 실행 안의 번호 중복, 모델이 스스로 낮춘 신뢰도(low)를 검사합니다. 차단 사유가 하나라도 있으면 저장을 거부하고 bot_alerts에 critical로 기록합니다.

04 OCR 검수 — 번호가 끊기면 시험에 못 들어간다

PDF에서 뽑은 문항은 번호 연속성, 번호 중복, 보기 5개, 보기 라벨 순서를 OCRReviewBot이 봅니다. 지적이 있으면 ocr_review_issues에 needs_review로 쌓이고, 5월 20일 커밋 “Prevent unreviewed OCR items from reaching exams” 이후 검수 전 문항은 시험 구성에서 빠집니다.

05 시험 조립 — 채점할 수 없는 문항은 저장 시점에 거부

주관식에 모범답안이 없거나 키워드 규칙이 비어 있으면 저장할 때 막습니다(“Surface ungradeable answers at save time”, “Enforce gradeable short-answer rubrics” — 둘 다 5월 20일). 나중에 채점 단계에서 터지는 것보다, 지금 저장이 안 되는 편이 낫습니다.

AI가 만든 코드에서 가장 값비싼 부분은 기능이 아니라 거부입니다. 기능은 요청하면 나오지만, 거부는 “무엇이 잘못된 것인지”를 내가 먼저 정의해야 나옵니다. — 5월 19~20일 커밋 로그를 다시 읽으며

04무료 티어에서 문항을 뽑는 법 — 한 번에 2문항

이 파이프라인에는 이상한 숫자가 박혀 있습니다. 실행 1회당 최대 2문항, 재시도 4회, 재시도 기본 간격 1,200ms, 실행 간 지연 1,200ms. 무료 Gemini 티어의 분당 한도를 넘지 않으려고 제가 직접 정한 값이고, questionGeneration.ts의 기본값으로 남아 있습니다.

const DEFAULT_GEMINI_MAX_RETRIES = 4;
const DEFAULT_GEMINI_RETRY_BASE_MS = 1200;
const DEFAULT_GEMINI_INTER_RUN_DELAY_MS = 1200;
const DEFAULT_GEMINI_MAX_QUESTIONS_PER_RUN = 2;

그래서 화면에서 “30문항”을 요청해도 실제로는 잘게 쪼개 반복합니다. 요청 상한은 30문항(getRequestedQuestionCount)이고, 목차별 계획(partPlans)을 주면 장별 문항 수까지 나눠 생성합니다. 5월 16일 커밋 “Support per-part question generation counts"가 그 기능입니다.

운영 문서에는 이렇게 적어 두었습니다. “Gemini의 한도는 API 키가 아니라 프로젝트 단위로 걸린다. 재시도는 일시적 스파이크를 완화할 뿐 할당량 천장을 없애지 않는다.” 그리고 기본 모델을 gemini-2.5-flash-lite로 둔 이유도 적어 두었습니다 — 대량·저비용 생성에는 무거운 모델보다 이쪽이 안전하다는 판단입니다. 그 위에 OpenAI(직접 PDF 입력 가능)와 로컬 Ollama(qwen2.5:7b-instruct, JSON 스키마 형식)를 같은 인터페이스 뒤에 두었습니다. 키가 없으면 수동 출제는 여전히 됩니다. LLM은 “자동 생성”에만 필요한 부품입니다.

실패를 기록하는 방식 — 빈 결과는 성공이 아닙니다. 5월 9일 “Fail empty question generation runs", 5월 16일 “Reject empty question generation results". 모델이 “문항 0개”를 돌려주면 잡은 failed로 끝나고, 화면에는 왜 끝났는지가 남습니다. AI 기능에서 가장 흔한 거짓말은 성공했다고 표시되는 실패입니다.

05문서에서 문항을 꺼내는 순서 — 텍스트가 먼저, OCR이 나중

가장 많이 고친 부분입니다. 5월 19일 하루에만 OCR 관련 커밋이 10개입니다. 결론부터 적으면 PDF에 텍스트가 있으면 OCR을 쓰지 않습니다.

  1. 1순위 pdftotext — PDF 안에 심어진 텍스트 레이어를 -layout 옵션으로 무손실 추출합니다. 한글이 깨지지 않고 빠릅니다.
  2. 2순위 pdftoppm + Tesseract — 스캔 이미지 PDF만 여기로 옵니다. 300 DPI로 렌더한 뒤 OCR합니다. 250 DPI에서 한글이 깨져 올린 값입니다.
  3. 3순위 ocrmypdf — 앞의 두 도구가 없을 때의 폴백.

스캔본을 다루는 쪽은 Python으로 따로 떼었습니다. FastAPI 워커 193줄이 하는 일은 세 가지입니다. 기울기 보정(cv2.minAreaRect로 각도를 재고, −45°를 넘는 값은 90° 보정), 2단 분할(세로로 나뉜 시험지 레이아웃을 좌·우로 잘라 읽기 순서를 맞춤), 그리고 작업 상태 조회(/job/{id}: 상태·진행률·메시지). 관리자 화면은 폴링으로 진행률을 봅니다. 같은 일을 하는 Node 로컬 서버(local-ocr-server.js 238줄)도 남아 있어서, Python 없이도 돌릴 수 있습니다.

여기서 얻은 교훈은 기술이 아니라 순서입니다. 처음에는 “스캔이든 아니든 OCR”이었고, 그 결과는 깨진 한글과 잘린 보기였습니다. 순서를 바꾸자 같은 문서에서 문항이 나왔습니다. 5월 19일 커밋 메시지에 그대로 남아 있습니다 — “PDF 텍스트 추출을 pdftotext(내장 텍스트 무손실 추출) 최우선으로 전환 — Tesseract OCR 한글 깨짐 근본 해결”.

06봇 네 마리, 378줄 — 감시를 사람이 아니라 코드에 맡긴 이유

5월 20일 오전 10시 39분, 커밋 하나에 봇 네 개가 들어왔습니다. 합쳐서 378줄입니다. 적은 줄임에도 이 프로젝트에서 가장 중요한 코드라고 생각합니다.

이 넷은 서로를 부릅니다. DataQualityBot과 OCRReviewBot은 문제를 찾으면 BugBot으로 경보를 올리고, SecurityBot도 medium 이상이면 BugBot에 넘깁니다. 그래서 관리자 화면에는 하나의 알림함만 있으면 됩니다. 출처가 다르고 심각도가 다른 사건이 한 줄씩 쌓입니다.

5월 20일 저녁 17:40에 “Harden bot alert ingestion"이라는 커밋이 하나 더 붙습니다. 클라이언트가 보내는 오류 로그는 공개 엔드포인트이므로, 본문 크기를 16,384바이트로 제한하고 초과하면 413으로 끊습니다. 로그를 받는 문은 좁게 열어야 합니다. 이 문으로 들어온 본문도 SecurityBot의 검사 대상입니다.

07채점은 산수, 해설은 AI

주관식 채점을 AI에 통째로 맡기면 같은 답안이 어제는 3점, 오늘은 2점이 됩니다. 국가시험을 준비하는 학생에게 그런 채점은 쓸 수 없습니다. 그래서 기본 채점기는 도메인 패키지의 순수 함수 95줄입니다.

  • 객관식은 정답 키와 정확히 일치할 때만 배점. 부분점수 없음.
  • 주관식은 키워드 규칙마다 “그 규칙의 키워드가 모두 답안에 있으면” 규칙 점수를 더하고, 금지 표현이 있으면 감점합니다. 총점은 0과 배점 사이로 자릅니다.
  • 모든 판정에 evidence가 붙습니다 — 규칙 ID, 라벨, 일치 여부, 점수 증감. “왜 2점인지”가 데이터로 남습니다.

AI는 그 위에 얹습니다. aiGrading.ts 525줄이 루브릭 평가(criteria·met·points·comment)와 해설(feedbackText·learningTips·keyConceptsMissed)을 만듭니다. 세 가지 원칙이 코드 주석에 그대로 적혀 있습니다.

배치 채점: 한 번의 LLM 호출로 전체 주관식 일괄 처리 / 캐시 우선: 피드백은 DB에 저장하고 같은 요청은 캐시 반환 / 그레이스풀 폴백: LLM 실패 시 키워드 채점 유지

이 원칙이 실제로 값을 합니다. Gemini가 503을 돌려줘도 학생은 키워드 채점 결과와 해설 캐시를 받습니다. 응답은 zod로 다시 검증하고, 형태가 깨진 항목은 기본값으로 채웁니다(점수 0, 근거 “AI 채점 근거가 제공되지 않았습니다”). AI가 죽어도 채점은 죽지 않습니다. 무료 티어를 쓰는 시스템에서 이건 선택이 아니라 설계 조건입니다.

08시험은 문항이 아니라 운영이다

시험 당일 아침에 문제가 되는 것은 문항이 아니라 사람입니다. 시험 코드를 모르는 학생, 와이파이가 끊긴 학생, 뒤로 갔다가 답안이 날아간 학생. 그래서 응시 쪽에 다음을 넣었습니다.

  • 명부와 토큰 — 학생 ID·이름·이메일 CSV를 올리면 응시 토큰과 초대 코드를 만들어 붙입니다. 초대 링크와 CSV를 내려받아 배포할 수 있습니다.
  • 공개 API의 최소 권한 — 학생이 부르는 경로는 시험 코드 조회, 응시 생성, 자동저장, 제출, 감독 이벤트, 이의제기, 본인 피드백뿐입니다. 관리자 경로는 x-api-key가 없으면 401입니다.
  • 답안 가리기 — 응시 화면에 내려가는 시험 객체에서 정답과 해설을 제거합니다(stripAnswers). 첫날 밤 P0 보안 커밋(d47190f)이 이 일을 했습니다.
  • 오프라인 답안 버퍼 — 브라우저 저장소에 draft·pending-submit·submitted 세 상태로 답안을 남깁니다. 네트워크가 끊기면 배너가 뜨고, 복구되면 버퍼에서 이어서 제출합니다.
  • 카운트다운과 봉인 — 시작 전 3·2·1·GO를 세고, 종료 시각 +60초가 지나면 시험이 봉인되어 새 응시를 받지 않습니다.
  • 감독은 영상이 아니라 기록 — 탭 전환(visibility-hidden·window-blur) 횟수, 진행률, 마지막 활동 시각을 모아 학생 타일마다 위험도를 계산합니다. 5분 이상 조용하면 idle, 위험이 높으면 suspicious. 웹캠은 쓰지 않습니다.

설계 문서의 문장을 그대로 옮기면 “무료 티어 안전성이 실시간 기능보다 우선한다 / 자동저장은 묶어서 굵게 / 주관식 채점은 규칙 기반이고 설명 가능해야 한다 / 부정행위 대응은 감사 우선, 영상 우선이 아니다”입니다. 22쪽짜리 설계 문서는 아니고 22줄입니다. 그 22줄이 이 프로젝트의 헌법이었습니다.

09문항분석 — 상위 27%와 하위 27%

시험이 끝나면 진짜 일이 시작됩니다. 좋은 문항과 나쁜 문항을 갈라야 다음 시험이 나아집니다. 이 시스템은 문항분석을 고전검사이론의 방식으로 계산합니다.

  • 난이도 지수 — 문항별 정답률. 객관식은 정답 키와 일치한 응시 수, 주관식은 배점의 60% 이상 받은 응시 수로 셉니다.
  • 변별도 지수 — 총점 상위 27%와 하위 27%를 잘라, 두 집단의 정답률 차이를 봅니다. 상위권이 맞히고 하위권이 틀리는 문항이 좋은 문항입니다.
  • 품질 신호 — 너무 쉽거나 너무 어려운 문항, 변별도가 낮은 문항, 이의제기가 몰린 문항, 생성에 실패한 문항에 표시를 답니다.

27%라는 숫자는 제가 임의로 고른 값이 아닙니다. 문항분석에서 상·하위 집단을 나눌 때 관행적으로 쓰는 비율이고, 응시 인원이 적을 때 상위 50%로 자르면 변별도가 납작해지기 때문에 이 값을 유지했습니다. 여기에 학생 개인 분석과 학습 경로가 붙습니다. 학생은 자기 취약 영역과 다음에 볼 문항을 받고, 그 결과는 student_analytics_cache에 만료 시각과 함께 저장됩니다.

이 절이 이 프로젝트에서 제가 가장 애정하는 부분입니다. AI가 문항을 만들어 주는 시대에 교수가 여전히 가치를 만들 수 있는 자리는 문항의 품질을 재는 일이기 때문입니다. 생성은 넘겨줄 수 있어도, 무엇이 좋은 문항인지 정하는 일은 넘겨줄 수 없습니다.

12디자인 문서는 페라리, 커밋은 트레이딩 플랫폼

design.md 370줄은 “Ferrari에서 영감을 받은 시네마틱 에디토리얼 시스템”입니다. 근검정 캔버스(#181818), 단일 액센트 로소 코르사(#da291c), 디스플레이 굵기 500 고정, 모서리 반경 0, 8px 간격 사다리(4/8/16/24/32/48/64/96/128). 그리고 “시험 응시 중에는 화려하게 만들지 말 것”이라는 제품 적응 규칙까지 적혀 있습니다.

그런데 5월 15일 커밋은 “Give CBT surfaces a trading-platform visual system"입니다. 디자인 문서는 페라리라고 하는데, 커밋은 트레이딩 플랫폼이라고 합니다. 둘 다 맞습니다. 관리자 화면에는 숫자가 많고, 숫자가 많은 화면은 결국 트레이딩 플랫폼처럼 생깁니다. 결국 남은 것은 styles.css 2,711줄과 AdminConsole.css 746줄, 응시 화면 734줄입니다. 시네마틱 에디토리얼은 “여백과 활자”로, 트레이딩 플랫폼은 “표와 숫자”로 구현됐고, 두 문서가 충돌한 자리는 대부분 표가 이겼습니다.

이 경험은 제게 익숙합니다. 11월에 카드뉴스를 만들며 “디자인 AI 슬롭이 심하다”는 질책을 두 번 받았습니다. 네온 그라데이션과 알록달록한 배지가 문제였습니다. 디자인 문서를 먼저 쓰는 것은 그 실수를 줄이는 가장 값싼 방법입니다. 이 시스템은 그걸 370줄로 먼저 해 두었고, 그래서 화면이 최소한 “AI가 만든 티”는 나지 않습니다.

13이 시스템이 남긴 세 문장

01 AI 시대의 품질은 프롬프트가 아니라 스키마에 있다

프롬프트를 아무리 정교하게 써도 모델은 흘립니다. 그래서 이 시스템은 프롬프트·zod 스키마·품질 봇·저장 차단·검수 게이트 다섯 겹을 두었습니다. 다섯 겹 중 네 겹은 AI가 아니라 코드입니다. 생성 품질을 올리는 가장 확실한 방법은 생성기가 아니라 거부기를 잘 만드는 것이었습니다.

02 무료 티어는 제약이 아니라 설계 조건이다

한 번에 2문항, 재시도 4회, 1.2초 간격. 이 숫자들은 기능을 줄였지만 시스템을 살렸습니다. 유료 결제 없이도 매일 문항을 쌓을 수 있었고, 무엇보다 실패해도 채점이 멈추지 않는 구조를 강제로 만들었습니다. 제약을 숨기면 나중에 청구서로 돌아옵니다.

03 시험 시스템의 정답은 문항이 아니라 절차다

학생이 기억하는 것은 “시험이 안 끊겼다”는 사실입니다. 그래서 오프라인 답안 버퍼, 자동저장, 봉인, 토큰, 401이 이 시스템의 절반입니다. 문항은 AI가 만들어도 되지만, 시험 당일의 절차는 사람이 정해야 합니다.

14한계 — 이 글이 확인하지 못한 것

이 연재의 규칙대로, 확인한 것과 확인하지 못한 것을 나눠 적습니다.

  • 테스트 197개 미실행. 이 환경에 Node.js·npm이 없습니다. npm test는 node --experimental-strip-types --test로 29개 테스트 파일을 돌리도록 짜여 있지만, 한 번도 실행하지 못했습니다. “테스트가 통과한다”고 쓸 수 없습니다.
  • 타입 검사·빌드 미실행. tsc -b와 워크스페이스 빌드를 돌리지 못했습니다. 라이브 번들이 존재한다는 사실만이 빌드가 어느 시점에 성공했다는 증거입니다.
  • 실제 데이터 미확인. 라이브 API는 상태 확인만 했습니다. 실제 과목 수, 문항 수, 응시 인원, 학생 개인정보는 조회하지 않았고 이 글에도 쓰지 않았습니다.
  • AI 생성 품질의 합격률 미측정. 봇이 몇 %를 막았는지, 생성된 문항 중 실제 시험에 쓸 수 있는 비율이 얼마인지 저장소에는 집계가 없습니다. 가장 알고 싶은 숫자인데 없습니다.
  • 구형 .doc 파서 없음. 운영 문서가 스스로 적어 둔 한계입니다. DOCX는 업로드되지만 전용 비-LLM 파서가 없어 제공자 파싱 품질에 의존합니다.
  • CORS 전체 허용. Worker의 CORS는 origin: "*"입니다. 관리자 경로는 키로 막지만, 키 하나를 공유하는 구조입니다. 학교 밖에 공개하는 서비스라면 도메인 제한과 키 회전이 필요합니다.
  • Codex 컴패니언의 로컬 의존. 관리자 화면의 “문항 품질·운영 진단·수정 제안·테스트 제안”은 로컬 에이전트(127.0.0.1:8791)를 부릅니다. 프로덕션 오리진에서는 차단되고, Vercel 경로로 옮긴 흔적은 있으나 실제 동작은 확인하지 않았습니다.
  • 응시 웹의 배포 경로. 11절에 적은 대로 vercel.json은 관리자 앱만 빌드합니다. 응시 화면이 별도 배포되는지 확인하지 못했습니다.

15Q&A

Q1AI가 만든 문항을 그대로 시험에 쓸 수 있나?

이 시스템의 답은 “아니오”입니다. 서버가 저장 단계에서 보기 5개·정답 1개·중복 지문·번호 중복·낮은 신뢰도를 검사해 하나라도 걸리면 저장을 막고, OCR로 만든 문항은 검수 승인 전까지 시험 구성에서 제외합니다. AI는 초안을 만들고, 시험에 들어가는 결정은 사람이 검수 화면에서 합니다.

Q2왜 한 번에 문항을 많이 만들지 않나?

Gemini 무료 티어의 분당 한도 때문입니다. 실행 1회당 최대 2문항, 재시도 4회, 1,200ms 간격이 기본값입니다. 요청은 30문항까지 받지만 잘게 쪼개 반복합니다. OpenAI나 로컬 Ollama로 바꾸면 같은 코드에서 상한을 올릴 수 있습니다.

Q3주관식 채점을 AI에게 맡기나?

기본은 키워드 규칙 기반 부분점수입니다. 점수 근거가 문항마다 남고, LLM은 루브릭 평가와 해설을 덧붙이는 보조로만 쓰입니다. LLM이 실패하면 키워드 채점 결과가 그대로 남습니다. 채점의 최종 책임을 모델에 넘기지 않는 것이 이 설계의 원칙입니다.

Q4같은 방식으로 학과 시험 시스템을 만들 계획이면 무엇부터 봐야 하나?

셋입니다. ① 채점 규칙을 먼저 문서로 — 키워드·금지어·배점이 정해지지 않으면 AI 채점도 검증할 수 없습니다. ② 거부 조건을 코드로 — 보기 개수·정답 범위·중복은 사람이 아니라 저장 경로가 막아야 합니다. ③ 시험 당일 절차를 기능으로 — 오프라인 버퍼와 자동저장은 “있으면 좋은 것”이 아니라 시험의 일부입니다.

16에필로그 — 22편을 닫으며

1편에서 저는 “1년에 시스템 22종”이라고 썼습니다. 이번 편이 그 22종 중 가장 조용한 시스템입니다. 화려한 데모도 없고, 눈에 보이는 애니메이션도 없고, 관리자 로그인 화면 뒤에서 대부분의 일이 일어납니다.

그런데 이 13일이 제게 남긴 것은 분명합니다. AI가 잘하는 일은 초안이고, 사람이 해야 하는 일은 기준이라는 것. 보기 5개, 정답 1개, 번호 연속, 중복 0 — 이 네 줄의 규칙을 코드로 옮기는 데 109커밋이 걸렸고, 그중 47개가 고치는 커밋이었습니다.

다음 편에서는 이 시스템의 미완을 정리해 보려 합니다 — 테스트 197개를 실제로 돌리고, 봇이 막은 비율을 집계하고, 응시 웹의 배포 경로를 하나로 정리하는 일. 그리고 마지막으로, 이 시스템이 학생의 합격률을 몇 퍼센트 올렸는지를 재는 일. 줄 수가 아니라 사람이 합격한 숫자를 세는 것이, 이 연재를 계속 쓰는 이유입니다.
